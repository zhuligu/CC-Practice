📌 本讲摘要

前 5 讲讲了 Skills 的具体写法与设计模式（第 10-14 讲）、本讲星火燎原——跳出 Claude Code 单产品视角、看 Skills 作为AI Agent 能力扩展机制如何从 1 个产品特性演变为行业开放标准。核心是 Agent Skills 协议：一个纯 Markdown 文件格式、在 125 天内被 OpenAI Codex、Cursor、GitHub Copilot、Windsurf 等主流 AI Agent 工具相继采纳、成为跨平台的能力描述语言。本讲讲清楚这件事为什么会发生、它改变了什么、以及工程师该如何把握标准化的机会。

本讲的三条主线：

第一、Skills 出圈的时间线——2024-10 Anthropic 推出 SKILL.md,2024-11 OpenAI Codex 采纳（命名为 Agent Skills),2024-12 Cursor 加入、2025-01 GitHub Copilot 采用、2025-02 行业形成跨平台协议、125 天从单产品特性到行业标准。

第二、为什么 Skills 能出圈——3 个根本原因（足够简单 / 足够强大 / 足够开放）、任何 AI 工具可解析、description 触发 + 渐进式披露的工程价值清晰、无专利可被任何工具采纳。

第三、对工程师和行业的双重影响——工程师写一次到处用、跨平台技能成为简历资产、行业差异化从有什么能力转向能力组合得有多好、技能市场可能形成（类似 NPM）。

学完本讲、你应该能看清 Skills 作为开放标准的战略意义、能用 Agent Skills 协议规范写出未来兼容的 SKILL.md、能把握标准化机会把团队能力沉淀成可跨平台分发的工程资产、能识别短期变现 vs 长期资产的认知陷阱。

Skills 出圈的时间线：125 天成为行业标准

2024-10：Anthropic 在 Claude Code 中推出 SKILL.md。这是一个看似低调的产品特性——纯 Markdown + YAML frontmatter、文件 5-10 行就能描述一个能力、LLM 看 description 匹配自动加载。没人预料到它会出圈。

2024-11：OpenAI Codex 采纳 SKILL.md 作为扩展机制、正式命名为Agent Skills。这是第一个跨厂商信号——OpenAI 作为 Anthropic 的直接竞争对手、竟然采纳了对手的格式、说明 SKILL.md 的设计真正击中了行业痛点。

2024-12：Cursor 加入支持。Cursor 是 AI IDE 领域的明星产品、对 AI Agent 能力扩展的需求最强、SKILL.md 让 Cursor 团队能在不重新发明轮子的情况下、获得 Claude Code 同款的能力扩展机制。

2025-01：GitHub Copilot 采用。GitHub 作为全球最大代码托管平台、采纳 Agent Skills 意味着 Skills 进入了行业基础设施层级——任何接入 Copilot 的开发者、都能用同样的 SKILL.md 写扩展。

2025-02：行业形成 Agent Skills 协议（跨平台互操作规范）。5 个主流 AI Agent 工具（Claude Code / OpenAI Codex / Cursor / GitHub Copilot / Windsurf）共同确认：同一份 SKILL.md 在所有平台都能用。125 天从单产品特性到行业开放标准。

这个速度在技术史上罕见——通常一个格式从产品特性到行业标准需要 3-5 年（JSON 用 5 年、Markdown 用 4 年、Kubernetes CRD 用 3 年）。SKILL.md 用了 125 天、因为它击中了AI Agent 能力扩展的真实痛点：每个工具都重新发明轮子（LangChain Tools / OpenAI Actions / AutoGPT Skills / Semantic Kernel Plugins)、重复造了 4 套、SKILL.md 提供了一个简单的、能用的、可共享的统一方案。

为什么 Skills 能出圈?3 个根本原因

SKILL.md 能成为行业标准、不是因为 Anthropic 推动（Anthropic 反而没刻意推动）、而是因为它具备 3 个根本特性、这些特性让任何 AI 工具都能零摩擦采纳。

原因 1：足够简单

SKILL.md 是纯 Markdown 文件 + YAML frontmatter、无任何运行时依赖。任何 AI 工具只要能读 Markdown + 解析 YAML就能支持——这是所有 AI 工具的基础能力、意味着零集成成本。

对比其他格式：OpenAI Actions 需要 OpenAPI schema 解析（中等集成成本）/ LangChain Tools 需要 Python 运行时（高集成成本）/ Semantic Kernel 需要 C# 插件注册（中等到高成本）。SKILL.md 只需要读文件、任何语言、任何平台、任何 AI 工具都能 5 分钟内集成。

原因 2：足够强大

SKILL.md 不只是格式简单——它有清晰的工程价值：description 触发（LLM 推理触发能力、无需代码注册）+ 渐进式披露（3 层加载、token 节省 91%+)+ Markdown 定义（纯文本、可 git 跟踪）。这 3 个特性解决了 AI Agent 能力扩展的 3 个核心痛点。

痛点 1：如何让 LLM 智能发现能力?——description 触发解决。

痛点 2：如何避免上下文爆炸?——渐进式披露解决。

痛点 3：如何让团队协作?——Markdown + git 解决。

3 个痛点都解决、SKILL.md 就成了AI Agent 能力扩展的事实标准。

原因 3：足够开放

SKILL.md 是无专利、无 Anthropic 专属协议的开放格式。任何 AI 工具都能采纳、不需要 Anthropic 授权、不需要付费、不需要遵守任何专有限制。OpenAI 作为竞争对手能采纳、本身就是开放性的最好证明。

对比：OpenAI Actions 虽然是 JSON schema、但隐含只能在 OpenAI 生态用的限制；LangChain Tools 绑定 Python 生态；Semantic Kernel 绑定 .NET 生态。SKILL.md 没有这些绑定、真正是无主的开放标准。

3 个原因（简单 / 强大 / 开放）叠加、SKILL.md 在 125 天内从单产品特性演变为行业开放标准。这是技术史上少见的自然演化案例——不是某家公司强推、而是市场自发达成共识。

Agent Skills 协议：跨平台互操作

Agent Skills 协议（2025-02 由 5 个 AI Agent 工具共同确认）规范了什么样的 SKILL.md 才是行业标准、任何工具按这个规范写、都能跨平台使用。

协议规范的 3 大块

1. 目录结构：.claude/skills/<name>/SKILL.md + references/（可选子目录）。根目录是 SKILL.md、深度文档放 references/ 子目录。命名规范：小写字母 + 连字符（不用下划线 / 空格 / 中文）。

2. frontmatter 4 字段：

• name：Skill 唯一标识、小写连字符、反映能力（sync-changelog / generate-api-docs）。

• description：何时触发 + 触发词、1-2 句话、1-100 字。

• license：可选、MIT / Apache-2.0 / Proprietary。

• allowed-tools：可选、工具白名单（Read / Edit / Bash 等）。

3. 触发机制：LLM 语义推理触发（description 匹配）、不依赖代码层注册。Claude / GPT / Copilot / Cursor 等所有 LLM 都能读 description 推理是否匹配。

跨平台互操作的 3 个工程价值

价值 1：写一次到处用。同一份 SKILL.md 在 Claude Code / OpenAI Codex / Cursor / GitHub Copilot / Windsurf 中都能用。工程师写一次、5+ 平台复用。

价值 2：团队协作零摩擦。SKILL.md 是 Markdown,git 跟踪、PR review 看 diff。团队内任何工程师都能贡献 Skill、跨项目复用。

价值 3：个人简历资产。懂 Agent Skills 协议 = 懂跨平台 AI 工具扩展。这是 2025-2026 年 AI 工程师的核心技能之一、比精通某一家 AI 工具更有价值。

3 个工程价值叠加、Agent Skills 协议成为AI 工程师的通用语——和懂 Git / Docker / Kubernetes在 2015-2020 年间的地位类似。

对工程师的 3 个影响

Agent Skills 协议出圈对工程师的工作方式产生 3 个深刻影响。

影响 1：写一次到处用

以前工程师要按平台学一套：学 LangChain 写 Python tool / 学 OpenAI Actions 写 JSON schema / 学 Semantic Kernel 写 C# 插件——每个平台一套、学不完。

现在只需学 SKILL.md——1 个格式、5+ 平台通用。学习成本从按平台 N 倍降为1 倍、但能用的平台从1 个扩为5+ 个。投资回报率（ROI）显著提升。

影响 2：跨平台技能成为简历资产

懂 Agent Skills 协议是 2025-2026 年 AI 工程师的硬通货。招聘 JD 里越来越多写熟悉 Agent Skills 协议 / 有 SKILL.md 编写经验——和 2020 年熟悉 Kubernetes在 SRE 岗位的地位类似。

工程师的策略：从现在起所有能力扩展都用 SKILL.md 写（无论用哪个 AI 工具）、沉淀成个人 / 团队的技能库、既是工程资产也是简历资产。

影响 3：Markdown + LLM 推理成为新的能力描述通用语

以前写工具 / 插件 / 扩展要学各种格式（JSON / Python / C# / YAML）。现在写 SKILL.md 就是写 Markdown + YAML——任何工程师、任何团队、任何公司都能贡献。

这个通用语让跨团队 / 跨公司的能力共享成为可能。开源 Skill 库（marketplace 类似 NPM）正在形成、未来 1-2 年可能出现AI Agent 技能商店——有人写 Skill 卖钱、有人用 Skill 省时间。

对行业的 3 个改变

Agent Skills 协议对行业产生 3 个结构性改变。

改变 1：AI Agent 工具的扩展机制趋同

5 个主流 AI Agent 工具都支持 Agent Skills 协议、意味着扩展机制不再是差异化的来源。差异化从有什么能力转向能力组合得有多好——就像智能手机的硬件趋同后、差异化转向 iOS vs Android 的生态。

AI Agent 工具的下一阶段竞争点：不是我有什么能力、而是我的能力组合有多好 + 我的 LLM 推理有多准 + 我的用户界面有多好。SKILL.md 是基础能力的通用语、真正决定胜负的是上层建筑。

改变 2：技能市场可能形成

类比 NPM(Node.js 包市场）、PyPI(Python 包市场）、Docker Hub（镜像市场）、未来 1-2 年可能出现AI Agent 技能市场——有人写 SKILL.md 卖钱（企业级数据分析 Skill / 行业基准 Skill / 安全审计 Skill)、有人用 SKILL.md 省时间（企业按月订阅行业 Skill 库）。

对工程师的影响：写通用 + 高频 + 标准化的 Skill 既是工程贡献也是潜在收入来源。但要注意短期变现 vs 长期资产的区分——Skills 出圈是长期工程资产积累、不是立刻发财。

改变 3：标准化降低学习成本

学会写一次 SKILL.md,5+ 平台通用、学习成本是 1 倍但收益是 5+ 倍。这降低了AI Agent 工具迁移的成本——团队从 Claude Code 迁到 Cursor 不需要重写所有扩展、SKILL.md 直接搬过去就能用。

降低学习成本反过来加速了行业演化——更多工程师愿意尝试不同 AI 工具、而不是被某一家绑定。这对整个 AI 行业是健康的（促进竞争、避免垄断）。

把握标准化机会的 3 个建议

对工程师 / 团队、把握标准化机会有 3 个具体建议。

建议 1：从现在起所有能力扩展都用 SKILL.md 写

无论你目前用哪个 AI 工具（Claude Code / Cursor / Copilot / Windsurf)、从现在起所有能力扩展都用 SKILL.md 写。这样未来跨平台迁移零成本——你的技能库是行业资产、不是某家工具的私有财产。

反面：继续写平台专属的扩展（LangChain Python / OpenAI JSON / Semantic Kernel C#)、这些格式在 2025-02 Agent Skills 协议确认后、正在变成历史包袱——未来跨平台时全部要重写。

建议 2：把团队内的高频 + 标准化能力沉淀成 Skill

团队内总有一些高频 + 标准化的能力（代码审查 / 测试覆盖 / 部署 / 数据库迁移）。把这些能力沉淀成 SKILL.md 模板、进 git + 配 PR review + 跨项目复用、形成可分发的工程资产。

原则：沉淀的是高频 + 标准化 + 跨项目可用的能力、不是某个项目特有的能力（后者留项目本地、不入团队 Skill 库）。

建议 3：关注 Agent Skills 协议的演进

协议还在演进（类似 LSP 在 2016-2018 年间的快速演化）、要持续关注规范变化。建议：

• 关注 Anthropic / OpenAI / GitHub 的官方博客、了解协议更新。

• 在 SKILL.md 里留出兼容性空间——不要用太激进的 frontmatter 字段（协议没确认的字段、可能未来被改）。

• 团队内做Skills 升级 PR——协议更新时、系统性地检查现有 SKILL.md 是否需要适配。

协议可能在 2026 年进一步规范化（类似 LSP 在 2018 年成为行业标准的过程）、早关注早受益。

⚠️ 常见坑

⚠️ 写了平台专属的 Skill（用 LangChain Python 或 OpenAI JSON、不通用）

最常见的标准化机会错过：用 LangChain 写 Python tool(@tool 装饰器）或 OpenAI Actions 写 JSON schema、这些格式在 2024-10 之前是主流、但 2025-02 Agent Skills 协议确认后、正在变成历史包袱——未来跨平台迁移时、这些 Python / JSON 格式全部要重写成 SKILL.md。修正：从 2025 年起、所有新写的能力扩展都用 SKILL.md。已存在的 Python / JSON 工具、看 ROI：如果跨平台复用价值高、改写成 SKILL.md；如果只是单平台使用、可以保留。判断标准：这个工具会被 2+ 个 AI 平台用吗?是 → 必须 SKILL.md；否 → 保留原格式也行。

⚠️ 以为 Skills 出圈 = 立刻发财（实际是长期工程资产积累、不是短期变现）

短期变现的认知陷阱：看到技能市场可能形成就以为可以靠写 Skill 立刻赚钱。实际上 Skills 出圈是长期工程资产积累、不是立刻发财。原因：技能市场还在早期（2025-2026)、付费意愿 / 监管 / 平台分成机制都不成熟。现实路径：把 Skills 当作工程贡献 + 简历资产沉淀（长期 ROI 高）、而不是短期变现工具。修正：不要被 FOMO 驱动乱写 Skill 想着卖钱、先想清楚这个 Skill 在我的团队 / 项目里真的高频 + 标准化吗?——是、值得写；否、跳过。

⚠️ 协议还在演进就锁死写法（要持续关注规范变化、留出兼容性空间）

锁死写法的风险：Agent Skills 协议还在演进（类似 LSP 在 2016-2018 年快速演化）、如果现在用了一些激进的写法（比如用协议没确认的 frontmatter 字段）、协议更新后可能不兼容。修正：用协议确认的标准字段（name / description / license / allowed-tools)、不用看起来好但未确认的字段。在 SKILL.md 里留出兼容性空间——避免用平台专属的扩展名 / 私有字段。判断标准：这个字段是协议确认的吗?是、可以用；否、慎用或加注释说明。

⚠️ 把团队内部 Skill 写成硬编码（不沉淀成可复用的 SKILL.md 模板、无法跨项目复用）

硬编码陷阱：团队内每个项目的 Skill 各自写一份、内容 80% 重复（sync-changelog / test-coverage / security-audit 几乎一样）、但因为项目结构不同 / 命名规范不同、无法复用。修正：把团队内的高频 + 标准化能力沉淀成 SKILL.md 模板、进 git + 配 PR review + 跨项目复用。原则：沉淀的是高频 + 标准化 + 跨项目可用的能力、不是某个项目特有的能力（后者留项目本地）。判断标准：这个 Skill 在 3+ 项目里都有?是 → 必须沉淀成模板；否 → 留项目本地。
