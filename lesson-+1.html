一个 BTC 价格循环的 30 分钟：Loop Engineering 最小可行单元

作者：[[zhuligu]] · 发布：2026-07-10
本文综合 4 篇 Loop Engineering 文章（《Claude Code 官方 Loops 上手指南》《Anthropic 内部方法论公开》《Loop 不是技巧是架构》《别调教 Prompt》）的共识，用一个 9 行 curl 的 BTC 价格监控循环演示最小可行单元（MVP）。前两节先把 Loop Engineering 的概念、演进、原理与工作机制讲清楚（不引入本文例子），第三节再把这个最小可行 Loop 落到 BTC 价格监控上，最后两节谈范式迁移与结语。

1 什么是 Loop Engineering —— 概念的提出与演进

2026 年 6 月，"Loop Engineering"这个概念在一周内被三位顶级工程师同时引爆：

  • Peter Steinberger（OpenClaw 作者）：别再给 Coding Agent 逐行写提示了，要设计让 Agent 自己循环运转的系统。
  • Boris Cherny（Claude Code 负责人）：他不再手动提示 Claude，而是写 Loop 让 Claude 自己运行。
  • Addy Osmani（Google Chrome 团队）：正式命名了这个概念——Loop Engineering。

三人指向同一个动作：设计的对象从"Agent 的单次行为"转变为"驱动 Agent 的完整系统"。 你不再是引擎，而是设计引擎的人。

Loop Engineering：替换你自己作为给 Agent 下指令的人，转而去设计一个能自动完成这件事的系统。

演进的四层范式：Loop 不是替代，是叠加

AI 工程化走过了四层，像带新人：

图 1-1：AI 工程化四层范式——上层包含下层，每层解锁新瓶颈

  • 第 1 层 Prompt Engineering：先教说话（"去查连接池超时的原因"），照做一次，下次换个问题还得再说。
  • 第 2 层 Context Engineering：再摆材料（喂代码库、文档、日志），更准但仍是你问一句答一句。
  • 第 3 层 Harness Engineering：再配工具（Shell、MCP、Git 权限），能自己查日志、改代码、跑测试，但每次都要你启动。
  • 第 4 层 Loop Engineering：最后写 SOP（每天自己扫、自己修、自己验），你只在关键节点审批。

每一层向上，关注的单元放大一号：从一句话，到一个窗口，到一次运行，最终到一个能自我运转的循环。

2 Loop Engineering 的原理与工作机制

这一节回答两个问题：Loop 由哪些零件组成？Loop 是怎么从一圈变成长期运转的？ Loop 看似只是"让 Agent 跑起来"，但跑得稳、跑得久、跑得不烧 token，需要一套相对完整的结构。下面四小节按"递进线 → 骨架 → 失败 → 何时该建"的顺序展开。

2.1 四种 Primitive：交出什么拿回什么

Anthropic 官方在《Getting started with loops》一文中，把 Loop 按"人需要持续介入哪些环节"分成四阶。每一阶的本质是：人交出某件事，Agent 拿回原本由人占用的注意力。 阶越高，人在链路里露脸的次数越少。下面这张表把每阶的"交出什么、拿回什么、用什么原语、怎么触发与停止"列了出来：

阶交出拿回原语触发 / 停止
1检查省去复查会话手动 / Claude 自判
2停止条件省去判断"够不够好"/goal手动 / 评估模型
3触发器省去手动启动/loop、/schedule时间 / 用户取消
4提示词省去人在链路三者组合事件 / 任务级退出

四阶不是平行选项，是阶梯。第 3 阶的 /loop 必须建立在第 1 阶已经能稳定产出之上——如果你连一次执行都没跑通，套上 /loop 也只是让错误以更高的频率重演。同理，第 4 阶的事件驱动建立在第 2 阶的目标评估之上——没有"什么算好"的定义，事件触发后也无从判断是否需要回滚。

大多数人想跳级——不行。 "Proactive 不是第五种 Loop，是前三者的编排产物。SKILL.md 没写就别幻想 Proactive。先走前三阶。"这是 Anthropic 工程师反复强调的次序：Turn-based → Time-based → Goal-based → Proactive，跳阶不是快，是失控。

2.2 五动作 × 六组件：Loop 怎么转起来

把 Loop 拆开看，一圈由五个动作依次串成：

动作作用
Discovery（发现）找出该做的事
Handoff（交接）隔离交给执行 Agent
Verification（验证）换个角度说不
Persistence（持久化）写到对话外
Scheduling（调度）让循环转起来

这五个动作不是并列的清单，而是一条因果链：调度触发发现 → 发现的结果被交接给执行者 → 执行后做独立验证 → 验证通过的事实被持久化 → 持久化结果进入下一轮调度的判断依据。任何一个环节缺位，下一环节就会失真——没有验证就持久化，等于把未确认的脏数据写进基线；没有持久化就调度，等于让 Agent 每天从零开始。

支撑这五个动作运转的，是六个组件（按依赖顺序：Connectors → Automations → Skills → Worktrees → Sub Agents → State）：

组件本质
Connectors感知外部世界
Automations调度器
Skills磁盘化的 SOP（SKILL.md）
Worktrees并行隔离
Sub Agents独立验证
State跨轮记忆

六个组件同样不是平行选项。Connectors 是地基——Agent 看不见外部世界，后面的所有动作都失去对象；Automations 在其之上，把"什么时候跑"变成可声明的调度；Skills 把每次执行的经验固化成 SOP，让下一轮不必重新解释规则；Worktrees 是并行的舞台，多任务时不互相覆盖；Sub Agents 是独立的判官，从另一个视角挑战主 Agent 的结论；State 是跨轮记忆，让今天的结果与昨天的结果可比。

五动作是"怎么转"，六组件是"由谁转"。缺一个，后面的都站不住。 这个判断也是后续 §2.3 失败模式的根据——失败不是神秘的运气差，而是某个动作或某个组件被悄悄跳掉。

2.3 五种失败模式：跳一个就歪

Loop 的失败不是随机的，而是五个动作中跳掉一个的必然结果：

跳过的动作失败模式症状
Verification点头循环（Nodding）几百轮从未说过"不"
Persistence失忆循环（Amnesiac）每天从零开始，无累积
Scheduling手动循环（Manual）演示完再没跑过
Discovery盲眼循环（Blind）人每天还在决定该做什么
Handoff纠缠循环（Tangled）并行 Agent 改同一目录

这五种模式不是五种 bug，而是五种被忽略的纪律：Nodding 是缺 Verification、Amnesiac 是缺 Persistence、Manual 是缺 Scheduling、Blind 是缺 Discovery、Tangled 是缺 Handoff。读完这张表可以反过来用：只要识别出循环当前的失败模式，就能直接定位应该补哪个动作/组件，不必每次重新排查找原因。

2.4 四格检验：什么时候该建 Loop

不是所有任务都值得建 Loop。在动手写 /loop 之前，先用下面这张四格检验问自己——每一格都是"如果回答是 No，循环一定会以某种特定方式失败"的硬约束：

格子检验项含义
1任务会重复吗单次任务不需要 Loop
2验证能自动化吗没人判"对错"的循环会跑歪
3Token 预算可承受吗持续推理会爆预算
4Agent 有高级工程师的工具吗没工具的循环只能空转

四格都过才适合建 Loop——这意味着任务的重复性、结果的判断力、资源的可持续、Agent 的执行能力全部具备，建出来的 Loop 才不会在几天内自然衰减。缺一格是 MVP 阶段的合理状态：它告诉你这个循环的极限在哪，而不是 bug。例如"任务会重复但验证不能自动化"的循环，第一格过、第二格缺，结果必然滑向 §2.3 的"点头循环"。这时与其抱怨循环不工作，不如承认"这是 MVP 阶段，把第二格补上是下一步"。

3 实践：BTC 价格监控的最小可行 Loop

完整生产级 Loop 动辄上千行工具链，覆盖日志扫描、CI、灰度、回滚、监控等几十个节点。但最小可行单元（MVP）长什么样？

本文用 9 行 curl + 1 段 prompt 的 BTC 价格监控循环，跑完 Loop Engineering 的最小可行演示——按 §2.1 的 Primitive 分阶看，是第 1 阶（手动 prompt）+ 第 3 阶（/loop 5m）的初级合体，还没到第 2 阶 Goal-based（没有评估模型），更没到第 4 阶 Proactive（没有事件驱动）。

3.1 五动作映射：Loop 的骨架长什么样

按 §2.2 的五动作模板，对照 BTC 例子：

动作定义BTC 例子对应
发现（Discovery）找出该做的事/loop 5m 触发 prompt
交付（Handoff）隔离交给执行者Claude 调用 Bash 执行 curl
验证（Verification）换个角度说不没有独立验证 ——Claude 自查自报
持久化（Persistence）写到对话外没有磁盘持久化 ——会话上下文是唯一记忆
调度（Scheduling）一圈圈自动转/loop 5m 间隔触发，"无显著变化"也是合法输出

缺两个动作（验证 + 持久化），但调度 + 发现 + 交付三件已足以让循环"看起来在转"。这恰好对应 §2.3 的失败模式——我的例子就处于"Manual Loop"和"Amnesiac Loop"的中间状态。

3.3 六组件：覆盖了哪些、缺了哪些

按 §2.2 的六组件，BTC 例子覆盖了 3 个，缺 3 个：

组件作用BTC 例子
Connectors感知外部世界curl + 本地代理（单层）
Automations调度器/loop 5m 会话内循环
Skills固化 SOP❌ 规则写在 prompt 里，未沉淀
Worktrees隔离并行❌ 单任务，不需要
Sub Agents独立验证❌ Claude 自查自报
State跨轮记忆❌ 仅会话上下文

缺 Skills / Sub Agents / State 这三件正是从 MVP 走到生产 Loop 的差距。它们不是 MVP 的问题，而是 MVP 的下一步。

3.4 Connectors：先让 Agent 看见外部世界

坑 1：默认 WebFetch 不可用。 我让 Claude 直接 WebFetch CoinGecko，被沙箱挡了：

Unable to verify if domain api.coingecko.com is safe to fetch.
This may be due to network restrictions or enterprise security
policies blocking claude.ai.

坑 2：默认 curl 也不可达。 切到 Bash + curl 后：

curl: (28) Connection timed out after 10013 milliseconds

解法：本地代理。 这台机器在国内网络环境，外部 API 全被 GFW 屏蔽。我让用户提供代理地址 127.0.0.1:7890，curl 加上 -x 参数后立刻通：

curl -x http://127.0.0.1:7890 \
  -sS --max-time 15 \
  "https://api.coingecko.com/api/v3/simple/price?ids=bitcoin&vs_currencies=usd,usd_24h_change&include_24hr_change=true"
# → {"bitcoin":{"usd":64413,"usd_24h_change":2.708002776454609}}

生产环境的 Connectors 层需要 6 层（数据访问→模型追踪→发布→通知→验证→基础设施），MVP 阶段只用 1 层（直接 curl 拿数据）。

3.5 Automations：用 /loop 而不是自己写 cron

两种调度方式：

方式命令行为
手动每次粘贴 promptTurn-based
/loop/loop 5m Time-based，会话内自动循环

/loop 的优势：会话级 + 短间隔 + 自带"立即执行一次"。它把"调度"这件事做成一个原语，不需要自己配 crontab，也不需要把 prompt 写成脚本。

我直接用 /loop 5m ——首次执行建立基线（"首次执行无基线，直接输出当前价格作为基线即可"），后续每次循环对比"变化 > 0.5%"。

3.6 Skills：把规则写在 prompt 里

我没有写 SKILL.md，规则直接写在 prompt 中：

对比上一次循环记录的价格：
- 如果本次价格相对上次变化幅度超过 0.5%，输出：新价格 USD、变化方向、
  变化幅度（%）、当前北京时间、24h 变化
- 否则只输出 "无显著变化"

首次执行无基线，直接输出当前价格作为基线即可。

这就是 Skill 的雏形 ——把"什么算有变化、什么算没变化"显式写下来。真正的 Skill 是磁盘化、可跨会话复用、可被多个 Agent 复用。我这个 prompt 还是"绑定在对话里的一次性规则"。

升级路径：把这段规则写到 ~/.claude/skills/btc-monitor/SKILL.md，下次开会话也能用。

3.7 缺的三个组件

缺什么为什么缺何时该补
Worktrees单任务无并行多个币种 / 多个交易所同时监控时
Sub Agents信任 Claude 自查加一个独立 agent 校验（如对比 Binance + CoinGecko 两源）
State会话上下文足够关掉会话还想延续时（写文件 / 写 SQLite）

Worktree / Sub Agent / State 在 MVP 阶段都可以缺，因为：

  • 单任务不需要隔离（Worktree 是给并行用的）；
  • 阈值规则简单可验证（Sub Agent 是给"修复者自证"用的，BTC 例子无修复环节）；
  • 会话期内不需要持久化（State 是给跨会话用的）。

3.8 实测：9 次 /loop 自动跑的数据

完整链路（一次循环）：

[/loop 5m 触发] 
   ↓ 触发 prompt
[Claude 收到 prompt] 
   ↓ 调用 Bash 执行 curl
[curl -x 127.0.0.1:7890 ...] 
   ↓ 返回 JSON
[Claude 解析 JSON]
   ↓ 对比会话历史里的"上次价格"
[分支：变化 > 0.5% ?] 
   ├── 是 → 主动报告：新价格、变化幅度、时间、24h
   └── 否 → 输出 "无显著变化"
   ↓ 基线更新（写到对话历史）
[5 分钟后再次触发]

沉默就是它该有的输出。

循环不是因为没人通知就坏了，沉默恰恰是它工作正常的证据。

4 范式迁移：从这个最小 Loop 到生产 Loop

4.1 这个循环的 4 个真实缺陷

缺陷 1：没有独立验证。如果 Claude 解析错了（比如 API 字段变了，它没注意到，仍然报"无显著变化"），循环会一直沉默下去。对策：加一个独立 agent 交叉验证（CoinGecko + Binance 两源比对）。

缺陷 2：没有持久化。会话关掉，基线消失。对策：把价格写入 ~/.btc-price-baseline 文件，下个会话读取；或写 SQLite。

缺陷 3：阈值是硬编码的。"0.5%" 对 $64,000 的 BTC 来说是 $320；对 $100,000 时是 $500。对策：改成绝对阈值 + 百分比阈值双轨（如"变化 > 0.5% 或 > $300"）。

缺陷 4：失败模式没处理。代理挂了、CoinGecko 限流、网络抖动，循环会怎样？对策：在 prompt 里加错误分支——"curl 失败时不要静默，记录失败次数，连续 3 次失败则主动告警"。

这四条都是《Anthropic 内部 Loop Engineering 方法论公开》一文说的"四种隐性成本"——验证债务、理解腐烂、认知投降、Token 爆炸——的微缩版。

4.2 给读者的行动清单：从 MVP 到生产

如果你想把这个 BTC 例子升级到生产级，按这个顺序走：

周做什么产出验收标准
1Connectors 地基curl → 脚本 → MCP server（封装 CoinGecko + Binance 两源）一条命令同时拿到两源价格
2Skills 沉淀把"什么算变化"写成 SKILL.md，包含 6 种行情异常分支跨会话复用，新开会话直接 cat ~/.claude/skills/btc-monitor/SKILL.md
3State 落盘价格写入 SQLite（或 JSONL），基线可追溯关掉再开，仍能接续
4Sub Agent 验证加一个独立 agent 做交叉校验 + 异常告警一次故意制造的数据错误能被捕获
5+Proactive 升级用 /schedule 搬到云端，事件触发而非时间触发7×24 不停机

4.3 我从这次 30 分钟里真正学到的 3 件事

第一，Loop 的门槛比想象低。9 行 curl + 1 句规则 = 一个能转的循环。不需要 9000 行工具链。

第二，Loop 的失败比想象多。网络、代理、API、阈值、持久化、验证——每一项都能让循环静默死掉。沉默 ≠ 正常，要时刻问"循环在真的转吗"。

第三，MVP 阶段不必追求 Proactive。Anthropic 官方文章反复强调："别跳级。先把 Turn-based 跑通，再 Time-based，再 Goal-based，最后才 Proactive。" 我的 BTC 循环就是 Turn-based + Time-based 的最低合规形态——这正是起点。

5 结语：别调教 Prompt，去设计 Loop

Anthropic 的工程师在公开方法论里说过一句话，我觉得对 MVP 阶段最重要：

Stop criteria 是 design variable。

写 Loop 之前先想清楚：什么算干完？谁来判？

我的 BTC 循环里：

  • 什么算干完 = 价格变化 > 0.5%
  • 谁来判 = Claude 自己（自查自报）

哪怕是这么简单的循环，这两件事也得想清楚。想不清楚的循环只会是"烧 token 的循环"。

最后抄一段我很喜欢的话收尾：

别再当循环里最慢的那一环——去设计循环。

30 分钟、9 行 curl、一个比特币价格监控循环——这就是 Loop Engineering 的最小可行单元。剩下的，是把单元连成网络，把网络长成系统。

curl -x http://127.0.0.1:7890 -sS --max-time 15 "https://api.coingecko.com/api/v3/simple/price?ids=bitcoin&vs_currencies=usd,usd_24h_change&include_24hr_change=true"

解析返回的 JSON，提取 bitcoin.usd（当前美元价）和 bitcoin.usd_24h_change（24小时涨跌幅 %）。

对比上一次循环记录的价格：
- 如果本次价格相对上次变化幅度超过 0.5%，输出：新价格 USD、变化方向（涨/跌）、变化幅度（%）、当前北京时间、24h 变化
- 否则只输出 "无显著变化"

首次执行无基线，直接输出当前价格作为基线即可。
