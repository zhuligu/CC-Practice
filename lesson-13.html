正课 第 13 / 33 讲 Claude Code 工程化实战 Skills + SubAgent + Commands

📌 本讲摘要

前 6 讲讲了 SubAgent 系列（第 4-9 讲）、第 10-12 讲讲了 Skills 系列。本讲进入"组合"——Skills + SubAgent + Commands 三件套不是孤立机制、而是可以联动的：Skills 给 SubAgent"喂能力"（作为上下文的一部分）,SubAgent 用 Skills 完成专项任务、Commands 触发整个流程。本讲讲 3 种组合模式（Skills 喂 SubAgent / SubAgent 内部用 Skills / 流水线组合）+ 2 个实战（代码审查专家 / 部署专家）、最后给出"先理解组合的全貌、再动手构建组件、最后组装成完整的专家"的工程方法论。

本讲的三条主线：

第一、组合的全貌——3 件套的 3 种关系（Skills 喂 SubAgent / SubAgent 内部用 Skills / 流水线组合）;3 种关系不是互斥、可以叠加形成专家系统。

第二、3 种组合模式的工程实现——能力注入（把 Skill 全文作为 system prompt)/ 动态加载（SubAgent 流程中按需加载 Skill)/ 流水线（用 Command 触发一连串 Skill）。

第三、2 个专家系统的组装实战——代码审查专家（Security-Audit + Style-Check + Test-Coverage 三个 Skill 喂给 Code-Reviewer SubAgent)/ 部署专家（Pre-Deploy-Check + Deploy + Rollback 三个 Skill 喂给 Deployer SubAgent、用 /release Command 触发整条流水线）。

学完本讲、你应该能区分 3 种组合模式的工程实现、能给代码审查 / 部署 / 文档生成等场景组装专家系统、能避免 3 件套职责不清和上下文爆炸两个常见陷阱。

📖 详细内容

组合的全貌：3 件套的 3 种关系

第 10 讲我们说 Skills / SubAgent / Commands 是 Claude Code 的 3 种能力扩展机制。本讲的核心命题：这 3 者不是孤立的、而是可以联动的。理解 3 种关系、是设计专家系统的前提。

3 种关系的全景图

关系 1：Skills 喂 SubAgent（能力注入）——把 Skill 的 SKILL.md 全文作为 SubAgent 的 system prompt 的一部分。SubAgent 启动时、已经把 Skill 的能力内化了。

关系 2：SubAgent 内部用 Skills（动态加载）——SubAgent 在执行过程中、根据任务需要、临时加载某个 Skill（用 description 匹配触发）。SubAgent 启动时不知道所有能力、按需扩展。

关系 3：流水线组合（Skill 链）——用 Command 触发一连串 Skill 顺序执行。每个 Skill 跑自己的、Skill 之间用文件 / 状态 / 任务队列通信。

3 种关系的核心区别在于能力的归属：

• 关系 1（注入）——能力在 SubAgent 启动时就长在身上,SubAgent 拥有完整知识。

• 关系 2（动态）——能力按需加载,SubAgent 体积小、能力按需扩展。

• 关系 3（流水线）——能力在多个独立实体之间流转、每个实体只负责自己的一段。

3 种关系不是互斥、可以叠加

一个复杂的专家系统可以同时用 3 种关系。典型架构：

1. 顶层用 Command 触发流水线（关系 3）。

2. 流水线的某一步调起 SubAgent(SubAgent 内部用 Skill——关系 2）。

3. SubAgent 启动时把核心 Skill 注入 system prompt（关系 1）。

三层叠加形成专家系统——顶层 Command 触发 → SubAgent 隔离上下文 → Skill 注入能力 → 动态加载补足 → 流水线跨阶段。后面代码审查专家和部署专家两个实战都是这套架构。

维度 模式 1：Skill 注入 模式 2：动态加载 模式 3：流水线
能力归属 SubAgent 启动时内化 SubAgent 执行时按需 多个 Skill 顺序流转
System prompt 大小 大（注入多） 小（只描述触发） N/A(Command 触发）
触发方式 SubAgent 启动即用 执行时 description 匹配 用户 /<command>
适用场景 单角色 3 维审查 多阶段按需能力 固定步骤流水线
灵活性 低（写死） 中（按需） 低（标准化）
复杂度 低（单一 SubAgent) 中（SubAgent + Skill 协调） 高（多步协调）

模式 1：Skills 喂 SubAgent（能力注入）

模式 1 的工程实现：把 Skill 的 SKILL.md 全文（或关键部分）作为 SubAgent 的 system prompt 的一部分、SubAgent 启动时就内化了这些能力。

实现方式

SubAgent 的 markdown 配置通常有 system prompt 字段。把 Skill 的核心内容写进 system prompt：

---
name： code-reviewer
description： Code review specialist that audits for security, style, and test coverage.
tools： Read, Grep, Glob, Bash
---
# Code Reviewer
## 你的能力
你是代码审查专家。每次审查按以下 3 步走：
### Step 1：Security Audit（注入自 security-audit Skill)
[这里嵌入 security-audit Skill 的核心内容]
- 检查 SQL 注入（原始 SQL 字符串拼接）
- 检查 XSS（未转义的用户输入）
- 检查 SSRF(URL 由用户控制）
- 检查硬编码密钥（api_key = "xxx")
- 检查危险命令（...| sh / chmod 777 / curl | bash)
### Step 2：Style Check（注入自 style-check Skill)
[嵌入 style-check Skill 的核心内容]
- PEP 8 合规（line length < 100、命名规范）
- 函数长度 < 50 行
- 注释覆盖率 > 30%
### Step 3：Test Coverage（注入自 test-coverage Skill)
[嵌入 test-coverage Skill 的核心内容]
- 新增代码必须有对应测试
- 行覆盖率 > 80%
- 边界 case 必须覆盖
## 输出格式
Markdown 报告、严格按 [Security | Style | Test] 3 段
```

这个 code-reviewer SubAgent 启动时、已经把 3 个 Skill 的核心内容内化在 system prompt 里。它审查代码时、直接用这些规则、不需要动态加载。

适用场景

SubAgent 总是需要这个能力（每次启动都用）。比如 code-reviewer 每次审查都需要 security / style / test 3 个维度、这 3 个 Skill 注入到 system prompt 最合适。

代价

SubAgent 的 system prompt 会比较大（3 个 Skill 的核心内容加在一起）。如果 SubAgent 启动慢、说明注入过多——该考虑用模式 2（动态加载）替代。

模式 2：SubAgent 内部用 Skills（动态加载）

模式 2 的工程实现：SubAgent 启动时 system prompt 不包含 Skill 内容、在执行过程中根据任务需要、临时加载 Skill。

实现方式

SubAgent 的 system prompt 写"如果你需要 X 能力、加载 skill-name",Claude 在执行过程中按需触发。

---
name： deployer
description： Deployment specialist. Run pre-deploy checks, deploy, and handle rollback.
tools： Read, Edit, Bash, Grep, Glob
---
# Deployer
## 你的工作流
### 阶段 1：Pre-Deploy Check（需要时加载 pre-deploy-check Skill)
如果任务涉及"部署前检查"、触发 pre-deploy-check Skill 加载其完整工作流。
### 阶段 2：Deploy（需要时加载 deploy Skill)
如果任务涉及"执行部署"、触发 deploy Skill 加载其完整工作流。
### 阶段 3：Rollback（需要时加载 rollback Skill)
如果部署失败、触发 rollback Skill 加载其完整工作流。
```

deployer 启动时 system prompt 较小（只描述何时触发哪个 Skill)、在执行过程中才按需加载 Skill 全文。好处：deployer 体积小、按需扩展、适用于能力多但每次只用一部分的场景。

适用场景

SubAgent 有很多潜在能力、但每次任务只用其中一两个。典型：deployer 平时只跑 deploy 阶段、失败时才需要 rollback Skill。

代价

依赖 description 写得准——如果某个 Skill 的 description 不准、deployer 可能不会触发它、导致漏做某步。修正：Skill 的 description 必须互斥且完备,deployer system prompt 里写如果...就加载...的触发条件必须清晰。

模式 3：流水线组合（Skill 链）

模式 3 的工程实现：用 Command 触发一连串 Skill 顺序执行。每个 Skill 跑自己的、Skill 之间用文件 / 状态通信。

实现方式

在 .claude/commands/release.md 定义流水线：

---
description： Run full release pipeline. Executes sync-changelog, run-tests, build, deploy in sequence.
---
# /release：发布流水线
## 流程
1. 加载 sync-changelog Skill（更新 CHANGELOG.md)
2. 加载 run-tests Skill（跑测试、失败则终止）
3. 加载 build Skill（构建产物）
4. 加载 deploy Skill（部署到生产）
5. 加载 notify Skill（通知团队）
## 错误处理
任一 Skill 失败、流水线暂停、通知用户。
```

用户输入 /release,Claude Code 顺序执行 5 个 Skill。每个 Skill 跑自己的（Skill 内部可能调 SubAgent / 用工具）,Skill 之间用文件 / 状态通信（比如 sync-changelog 把更新结果写到 CHANGELOG.md,deploy Skill 读 CHANGELOG.md 拿到版本号）。

适用场景

有一连串固定步骤、每步都有明确的输入输出、用户希望一个命令触发整条流水线。典型：发布流水线（CI 自动化场景）/ 审查流水线（用户主动审查场景）/ 数据分析流水线（分析师一连串 ETL）。

代价

流水线的灵活性差——如果中间某步需要跳过或重做、得改 Command 文件。所以流水线适合高度标准化的流程、不适合高度定制的流程。

实战：代码审查专家的组装

第一个实战：用 3 件套组装代码审查专家。

角色清单

• 3 个 Skill：security-audit(SQL 注入 / XSS / SSRF / 硬编码密钥 / 危险命令）/ style-check(PEP 8 / 函数长度 / 注释覆盖）/ test-coverage（新增代码有测试 / 覆盖率 > 80% / 边界 case)

• 1 个 SubAgent：code-reviewer（代码审查专家、综合 3 个 Skill 的输出）

• 1 个 Command：/review（用户主动触发、完整审查流程）

组合关系

用模式 1(Skills 喂 SubAgent)——把 3 个 Skill 的核心内容作为 code-reviewer 的 system prompt 的一部分。code-reviewer 启动时已经内化了 3 个维度的审查规则、审查时直接用。

触发流程

1. 用户输入 /review、触发 Command。

2. Command 调起 code-reviewer SubAgent。

3. code-reviewer 启动、system prompt 包含 3 个 Skill 的核心内容。

4. code-reviewer 读 git diff、按 Security → Style → Test 3 段输出报告。

5. 报告写 .claude/reports/review-<date>.md。

整套系统用户 1 个命令、得到 1 份完整审查报告、中间不需要用户介入。

为什么不模式 2（动态加载）

code-reviewer 每次审查都需要 3 个维度、没有按需的场景。所以 3 个 Skill 注入到 system prompt 最合适、不用动态加载。如果用模式 2、反而每次要扫描 3 个 Skill description 再决定加载哪些、增加延迟。

为什么不模式 3（流水线）

代码审查是一个角色做一件事、不是多步流水线。流水线适合步骤之间有数据流转、审查没有——1 份代码、3 个维度、1 份报告、中间无状态。所以 SubAgent（模式 1 注入）更合适。

实战：部署专家的组装

第二个实战：用 3 件套组装部署专家。

角色清单

• 3 个 Skill：pre-deploy-check（部署前检查清单）/ deploy（执行部署、带 Hook 兜底）/ rollback（回滚到上一版本）

• 1 个 SubAgent：deployer（部署专家、根据部署阶段加载不同 Skill)

• 1 个 Command：/release（发布流水线、4 步：测试 → 构建 → 部署 → 通知）

组合关系

用模式 2(SubAgent 内部用 Skills)+ 模式 3（流水线）的组合——deployer 启动时 system prompt 较小、执行过程中按需加载 Skill;/release Command 触发整条流水线。

触发流程

1. 用户输入 /release、触发 Command。

2. Command 跑流水线 4 步：加载 run-tests Skill → 加载 build Skill → 调起 deployer SubAgent → 加载 notify Skill。

3. deployer 启动、根据部署前 → 部署 → 回滚 3 阶段动态加载对应 Skill：

• 阶段 1（部署前）→ 加载 pre-deploy-check Skill。

• 阶段 2（部署中）→ 加载 deploy Skill。

• 阶段 3（失败回滚）→ 加载 rollback Skill。

4. 每步的输出写状态文件 .claude/state/release.json、供下一步读取。

5. 完成后、notify Skill 通知团队。

整套系统用户 1 个 /release 命令、得到 1 个完整发布流程、中间不需要用户介入（除了危险操作的人工确认）。

实战场景 使用的模式 Skill 清单 SubAgent Command
代码审查专家 模式 1（注入） 3：security-audit / style-check / test-coverage code-reviewer(3 Skill 注入 system prompt) /review
部署专家 模式 2（动态） + 模式 3（流水线） 3：pre-deploy-check / deploy / rollback + 2：run-tests / build / sync-changelog / notify deployer（按需加载 3 Skill) /release

为什么模式 2 + 3 组合、不用模式 1

deployer 的 3 个 Skill 不会同时用到（部署前 / 部署中 / 失败回滚是 3 个独立阶段）。如果用模式 1 注入、3 个 Skill 的内容占 5K tokens,deployer 启动慢、上下文满。用模式 2 动态加载、每次只加载当前阶段需要的 1-2 个 Skill、体积小、按需扩展。

同时、/release 流水线有 4 步、步骤之间有数据流转（测试结果 → 构建 → 部署 → 通知）、用模式 3 流水线最合适。

2 个实战的对比：代码审查专家是单角色 3 维审查用模式 1；部署专家是多阶段流水线 + 按需能力用模式 2 + 3。不同场景用不同组合、不要一刀切。

📄 第 13 讲配套：Skills 喂 SubAgent 的 system prompt 注入（把 Skill 全文作为 system prompt 的一部分）

---
# .claude/agents/code-reviewer.md
name： code-reviewer
description： Code review specialist. Audits for security, style, and test coverage in one pass.
tools： Read, Grep, Glob, Bash
model： sonnet
---

# Code Reviewer

## 你的能力
你是代码审查专家。每次审查按 Security → Style → Test 3 步走,综合输出报告。

## Step 1：Security Audit
[注入自 security-audit Skill]
- 检查 SQL 注入：搜 \`(SELECT|INSERT|UPDATE|DELETE).*\\+|f[\"'].*SELECT`
- 检查 XSS：搜 `innerHTML|dangerouslySetInnerHTML|v-html`
- 检查 SSRF：搜 `requests.get\\(user_url\\)|urllib.request.urlopen\\(url\\)`
- 检查硬编码密钥：搜 `(api_key|secret|password|token)\\s*=\\s*[\"']`
- 检查危险命令：搜 `\\|\\s*(sh|bash|sudo)|chmod\\s+777|：(){：|：&};：`

## Step 2：Style Check
[注入自 style-check Skill]
- PEP 8 合规：line length < 100
- 命名规范：snake_case 函数 / PascalCase 类 / UPPER_CASE 常量
- 函数长度 < 50 行
- 注释覆盖率 > 30%

## Step 3：Test Coverage
[注入自 test-coverage Skill]
- 新增代码必须有对应测试文件
- 行覆盖率 > 80%(用 pytest-cov)
- 边界 case 必须覆盖(空 / None / max / 异常)

## 输出格式
```markdown
# Code Review： <branch>
## Security： PASS/FAIL
- Critical： N
- Warning： N
## Style： PASS/FAIL
- 违规数： N
## Test： PASS/FAIL
- 覆盖率： X%
- 缺测： [文件名：行号]
## Verdict： APPROVE / REQUEST_CHANGES
```

📄 第 13 讲配套：SubAgent 内部用 Skills 的动态加载（在 SubAgent 流程的某一步调 Skill)

---
# .claude/agents/deployer.md
name： deployer
description： Deployment specialist. Runs pre-deploy check, deploy, and rollback on demand.
tools： Read, Edit, Bash, Grep, Glob
model： sonnet
---

# Deployer

## 你的工作流(按需加载 Skill)
deployer 启动时体积小,在执行过程中按需加载 Skill。

### 阶段 1：Pre-Deploy Check
**触发条件**：任务涉及"部署前"或"pre-deploy"
**加载 Skill**：pre-deploy-check
加载后,按 pre-deploy-check Skill 的工作流跑检查清单。

### 阶段 2：Deploy
**触发条件**：阶段 1 通过 + 任务涉及"部署"
**加载 Skill**：deploy
加载后,按 deploy Skill 的工作流跑部署。

### 阶段 3：Rollback
**触发条件**：阶段 2 失败
**加载 Skill**：rollback
加载后,按 rollback Skill 的工作流回滚。

## 状态文件
所有阶段结果写 .claude/state/release.json：
```json
{
  "stage"： "pre-deploy | deploy | rollback | done",
  "result"： "success | failure",
  "artifacts"： ["build/...", "image：..."],
  "rollback_to"： "<commit-hash>"
}
```
---
# .claude/skills/pre-deploy-check/SKILL.md
name： pre-deploy-check
description： Run pre-deployment checks (tests, lint, security scan) before deploying to production. Use when deployer is in pre-deploy stage.
disable-model-invocation： true
allowed-tools： Read, Bash
---

# Pre-Deploy Check

## 流程
1. 跑测试：`pytest tests/ -v`(失败则终止)
2. 跑 lint：`ruff check src/`(失败则终止)
3. 跑安全扫描：`bandit -r src/`(高危漏洞则终止)
4. 检查 CHANGELOG.md 是否已更新
5. 检查当前版本号 > 上一版本号

## 硬约束
- 任一检查失败 → 终止,不继续部署
- 不自动跳过任何检查

📄 第 13 讲配套：流水线组合的 Command 定义（/release 跑 4 个 Skill)

---
# .claude/commands/release.md
description： Run full release pipeline. Tests, build, deploy, notify.
---

# /release：发布流水线

## 流程
按顺序执行以下 5 步,任一失败立即终止：

1. **加载 sync-changelog Skill**
   - 更新 CHANGELOG.md 从 git commits
   - 输出：CHANGELOG.md 已更新

2. **加载 run-tests Skill**
   - 跑完整测试套件
   - 失败 → 终止

3. **加载 build Skill**
   - 构建产物(docker image / wheel / npm package)
   - 输出：image：tag / package.tar.gz

4. **调起 deployer SubAgent**
   - deployer 按需加载 pre-deploy-check / deploy / rollback Skill
   - 部署到生产
   - 失败 → rollback + 终止

5. **加载 notify Skill**
   - 通知团队(Slack / 邮件)

## 状态文件
所有步骤结果写 .claude/state/release.json：
```json
{
  "started_at"： "...",
  "steps"： [
    {"name"： "sync-changelog", "result"： "success"},
    {"name"： "run-tests", "result"： "success"},
    {"name"： "build", "result"： "success"},
    {"name"： "deploy", "result"： "success"},
    {"name"： "notify", "result"： "success"}
  ],
  "verdict"： "success"
}
```

## 用户操作
- 输入 `/release` 触发整条流水线
- 任何步骤失败,流水线暂停,询问用户是否继续

# Code Reviewer

## 你的能力
你是代码审查专家。每次审查按 Security → Style → Test 3 步走。

### 注入自 security-audit Skill
- SQL 注入：搜 `\\+.*SELECT|f[\"'].*SELECT`
- XSS：搜 `innerHTML|dangerouslySetInnerHTML`
- SSRF：搜 `requests.get\\(user_url\\)`
- 硬编码密钥：搜 `(api_key|secret)\\s*=\\s*[\"']`
- 危险命令：搜 `\\|\\s*(sh|bash)|chmod\\s+777`

### 注入自 style-check Skill
- line length < 100
- 命名：snake_case / PascalCase / UPPER_CASE
- 函数 < 50 行
- 注释 > 30%

### 注入自 test-coverage Skill
- 新增代码必须测试
- 覆盖率 > 80%
- 边界 case 覆盖

## 报告模板
```markdown
# Code Review： <branch> @ <commit>
## Security： PASS/FAIL
- Critical： N
- Warning： N
## Style： PASS/FAIL
- 违规： N
## Test： PASS/FAIL
- 覆盖率： X%
## Verdict： APPROVE / REQUEST_CHANGES
```

# /review：代码审查

## 流程
1. 调起 code-reviewer SubAgent(注入 3 个 Skill)
2. code-reviewer 读 git diff
3. 按 Security → Style → Test 输出报告
4. 报告写 .claude/reports/review-<date>.md
5. 询问用户是否要修复发现的问题(用 ask 机制)

## 硬约束
- 不跳过任何维度
- Critical 问题必须 REQUEST_CHANGES
- 报告格式严格按模板

⚠️ 常见坑

⚠️ Skills 喂 SubAgent 时把全部 Skill 塞进去（SubAgent 上下文爆炸）

常见的过度注入：SubAgent 启动时把 5-10 个 Skill 的核心内容全塞 system prompt、占 8K-15K tokens。结果——SubAgent 启动慢、上下文迅速占满、注意力分散。修正：模式 1 适合总是用到的能力（2-3 个 Skill 核心内容、占 2K-3K tokens)；超过 3 个、用模式 2（动态加载）。判断标准：SubAgent 的 system prompt > 4K tokens = 该用动态加载。

⚠️ SubAgent 内部动态加载 Skill 时没控制好触发条件（Skill 误触）

动态加载的触发失控：SubAgent system prompt 写需要时加载 X Skill、但没明确需要时是什么。结果——Claude 推理时自由发挥、经常误触发（比如看到数据库就加载 db-skill、实际任务和数据库无关）。修正：SubAgent system prompt 里明确如果...就加载...的触发条件、Skill 的 description 也写何时触发（第 10 讲规则）。判断标准：SubAgent 经常加载不该加载的 Skill?修触发条件。

⚠️ 流水线组合没考虑错误传播（任一 Skill 失败、流水线不暂停）

流水线的错误吞没：/release 流水线 4 步、run-tests Skill 失败了但流水线继续跑后续 build / deploy / notify、结果——部署了一个测试失败的版本。修正：每步检查上一步的 result、失败则立即终止 + 通知用户。判断标准：流水线有没有 try/except 机制?没有、补上。

⚠️ 3 件套职责不清（同样的功能既在 Skill 又在 SubAgent、改一处忘一处）

3 件套的职责重叠：某功能既写在 security-audit Skill 里、又写在 code-reviewer SubAgent 的 system prompt 里（模式 1 注入）。结果——某天发现安全检查要更新、改了 Skill 忘了 SubAgent、两份内容不一致。修正：严格分层——Skill 写完整工作流（触发时加载）,SubAgent system prompt 只写何时加载 + 用哪个 Skill（索引）、不要复制 Skill 的内容。判断标准：同一信息是否在 Skill + SubAgent 两处都出现?是、职责重叠、删一处。

💡 一句话备忘

Skills + SubAgent + Commands 三件套的 3 种组合模式（注入 / 动态 / 流水线）不是互斥而是叠加——用模式 1 注入常用能力、用模式 2 动态加载按需能力、用模式 3 触发流水线,三层叠加形成可复用的专家系统。
