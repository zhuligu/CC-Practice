正课 第 10 / 33 讲 Claude Code 工程化实战 Skills 系列开篇

📌 本讲摘要

本讲是 Skills 系列的开篇、核心目的是把"Skills 是什么、怎么写、怎么触发"讲透。Skills 和前 6 讲讲的 SubAgent 是 Claude Code 的两种"能力扩展"机制、但触发方式截然不同：SubAgent 由主对话显式调起（@code-reviewer),Skills 由 LLM 推理"自动发现并逐渐加载"——Claude 看到 description 匹配、自动加载整个能力包、用户都不用动手。

本讲的三条主线：

第一、Skills 是什么?和 SubAgent 的本质区别——Skills = 自动发现的能力包（LLM 推理触发、渐进式披露、零调用成本）;SubAgent = 显式调起的角色（@name 触发、独立上下文、固定启动成本）；两者互补不冲突。

第二、SKILL.md 的两段式结构——frontmatter（元数据、启动时全量加载）+ 正文（详细说明、触发时按需加载）；关键是 description 字段必须写成"何时触发"而不是"做什么"。

第三、Skills 和 SubAgent / Commands 的边界——Commands 用户主动调（斜杠命令）/ SubAgent 主对话显式调（@name)/ Skills LLM 自动发现（description 匹配）;3 者触发机制完全不同、不要混用。

学完本讲、你应该能写出第一个 SKILL.md（包含正确的 frontmatter 和三层正文结构）、能用 description 触发词让 Claude 自动加载、能判断"这个能力该写成 SubAgent / Command 还是 Skill"、能用渐进式披露节省 50% 的 token 开销。

📖 详细内容

Skills 是什么?和 SubAgent 的本质区别

Claude Code 有 3 种"扩展能力"的机制：Commands（用户主动调、斜杠命令）、SubAgent（主对话显式调、@name）、Skills(LLM 自动发现、description 匹配）。前 6 讲我们讲了 SubAgent、本讲进入 Skills 系列。

Skills 和 SubAgent 的核心区别在于"触发方式":

SubAgent：显式调起

用户必须主动说"用 code-reviewer 审查"、或主对话里说"@code-reviewer"。没有"自动"。每次调起都有 5-15 秒的固定成本（加载 system prompt + 启动独立上下文）。

Skills：自动发现

用户不需要"点名"。Claude 在推理时自动看用户的话、匹配 SKILL.md 的 description、如果匹配则自动加载整个能力包。零启动仪式、零用户操作。代价：Skills 的 description 在每次 Claude 推理时都被看到（占 token、但很小）。

可以这样理解：SubAgent 像"公司里你认识的人"——你得自己走过去说"帮我看下这段代码";Skills 像"公司里贴的标语 / 文档"——你自己走过去就能看到、需要时自动想起、不需要时"它就在那里但你不会注意到"。

Skills 的核心价值：

1. 零调用成本——用户不用记命令、不用 @name,Claude 自动识别该用哪个 Skill。

2. 渐进式披露——frontmatter 几十行（启动时加载）+ SKILL.md 正文几百行（触发时加载）+ 深层引用几千行（按需加载）;3 层叠加、token 成本最优。

3. LLM 推理触发——description 写得越具体、Claude 越能在合适的时机"想起"这个 Skill；写得越模糊、触发率越低。

Skills 不是 SubAgent 的替代——两者是互补关系。一个复杂任务、主对话可以先调起 SubAgent 跑（隔离上下文）,SubAgent 内部再用 Skill 加载专项能力（渐进式披露）。这是 Claude Code 的"分层能力调用"模式。

frontmatter 全解析：4 个核心字段

SKILL.md 顶部是一段 YAML frontmatter、声明 Skill 的元数据。共 4 个核心字段、每个都有讲究：

字段 1:name

Skill 的唯一标识、小写字母 + 连字符。命名规则：反映能力而非技术。建议：sync-changelog / generate-api-docs / audit-security / write-tests。反例：skill1 / myskill / sync（技术而非能力、同名易冲突）。

字段 2:description（关键中的关键）

这是"自动触发器"——Claude 在每次推理时看用户的话、匹配 description、如果匹配则自动加载 SKILL.md 正文。description 写错 = 触发率 = 0。

写法：必须写"何时触发"而不是"做什么"。

反例 1:description="A changelog generator"。❌ 描述了"做什么",Claude 不知道"用户什么时候需要"我。

反例 2:description="Syncs files"。❌ 太短、太模糊、什么场景都"匹配"也什么都"不匹配"。

正例：description="Update CHANGELOG.md from git commits since the last release. Use when user says '更新 changelog' / 'sync changelog' / 'release notes'."

三个要素齐全：触发时机（Update from git commits since last release)/ 动作（Update CHANGELOG.md)/ 触发词（'更新 changelog' / 'sync changelog' / 'release notes' 中英文都列）。

再举几个正例感受一下：

• "Generate API documentation from Python docstrings. Use when user says '生成 API 文档' / 'sync api docs' or after src/ changes."（生成 API 文档）

• "Audit code for security vulnerabilities (SQLi, XSS, SSRF, hardcoded secrets) before merging to main."（安全审计）

• "Write unit tests for new functions. Use when user adds new code without tests."（写测试）

字段 3:license

可选、声明 Skill 的许可证（MIT / Apache-2.0 / Proprietary 等）。团队内部用可以省略、开源发布建议明确。

字段 4:allowed-tools

可选、声明 Skill 加载时可用的工具（Read/Edit/Bash 等）。如果不写、Skill 加载时继承主对话的工具全集（没限制）；如果写了、Skill 内只看到声明的工具（更安全）。

4 个字段里、description 是灵魂、其他是修饰。description 写对了、Skill 才有"自动发现"的价值；写错了、就是一份"死文档"。

SKILL.md 正文结构：渐进式披露

frontmatter 下面是 SKILL.md 的正文——详细说明本 Skill 能做什么、怎么用、有什么坑。这是"触发时才加载"的部分、应该写得"机器可读 + 人可读"、而不是冗长的散文。

推荐 3 层结构：

第 1 层：快速参考（5-10 行）

用列表 + 简短说明、给 Claude 一眼看出"我该做什么"。比如：

## 快速参考
1. 读 git log --oneline -50 （取最近 50 个 commit)
2. 按 Conventional Commits 分类
3. 追加到 CHANGELOG.md 的 [Unreleased] 段
4. 如果 [Unreleased] 段已发布、新建 [版本号] 段

这一层是"操作清单",Claude 加载 Skill 后第一时间读这个、知道"先做什么后做什么"。

第 2 层：详细步骤（30-50 行）

把第 1 层的每一步展开、加细节（参数、命令、错误处理）。比如：

## 详细步骤
### 1. 读 git log
- 跑 `git log --oneline -50 --pretty=format:"%h %s"` 拿 commit hash + 标题
- 如果仓库是 monorepo、加 `-- ` 限定到子项目
- 如果 commit 多于 50、加 `--since="3 months ago"` 限定时间

### 2. 分类
- feat: 新功能
- fix: bug 修复
- refactor: 重构（无功能变化）
- docs: 仅文档
- chore: 杂项
- ...

### 3. 追加到 CHANGELOG.md
- 打开 CHANGELOG.md
- 找到 [Unreleased] 段（没则创建）
- 按"### feat / ### fix / ### refactor"子标题分类追加
- 每条带 commit hash（用反引号包起来）

这一层是"操作手册",Claude 实际操作时按这个执行。

第 3 层：边界 case + 反例（50-100 行）

列出常见坑、边界 case、典型反例。这是 Claude 遇到"规则没说清楚"的情况时的兜底参考。

## 边界 case
- 第一个 commit / 仓库没 CHANGELOG.md: 提示用户"是否要初始化?"(ask 机制）
- commit message 写得不规范（没有 Conventional Commits 前缀）：归到"chore"或"other"段、提示用户后续整改
- 同一个 commit 涉及多个类别（比如既改 src 又改 docs)：归到主类别（看 src 变化还是 docs 变化大）
- 已发布版本的 changelog 被改：拒绝、提示"已发布版本不可改"

## 反例
- ❌ 把所有 commit 拼成一段散文（应该按类别分小标题）
- ❌ 跳过分类直接追加（读者找不到自己关心的类别）
- ❌ 修改已发布版本的 changelog（应该新建版本段）

3 层叠加、SKILL.md 的总长度控制在 100-200 行最佳。超过 300 行就该拆——把第 3 层（边界 case）拆到 `references/` 子目录、SKILL.md 里只引用"详见 references/edge-cases.md"。这是 Skills 的"按需加载"设计：大多数情况 Claude 只读第 1-2 层就够了、边缘情况才读第 3 层。

Skills vs Commands vs SubAgent 怎么选?

新人最常问的问题："我手头这个能力该写成 Skill、SubAgent 还是 Command?"——答案是看"触发方式":

用 Command 的场景

用户主动调起、有明确的固定操作。典型：/test（跑测试）/ /commit(commit 改动）/ /deploy（部署）。Command 的优势：用户显式知道自己在调什么、有明确的"执行反馈"；劣势：用户得记住命令。

用 SubAgent 的场景

主对话里显式调起（@name 引用）、需要独立上下文隔离。典型：code-reviewer / test-runner / pr-drafter。SubAgent 的优势：独立上下文、可配工具白名单、可并行；劣势：每次启动 5-15 秒固定成本。

用 Skill 的场景

LLM 自动识别该用、不需要用户显式调。典型：更新 changelog / 生成 API 文档 / 写测试 / 安全审计。Skill 的优势：零调用成本、渐进式披露；劣势：依赖 description 写得准、触发率不一定 100%。

3 者的边界判断心法：

1. "用户会主动调吗?"——是 → Command

2. "需要隔离上下文或配工具白名单吗?"——是 → SubAgent

3. "其他情况（LLM 推理该用就用）"——是 → Skill

3 者是互补关系。一个项目可以同时有：Command（用户主动调的命令）/ SubAgent（主对话显式调的角色）/ Skill(LLM 自动发现的能力）3 种扩展能力共存。

维度 Command SubAgent Skill
触发方式 用户主动（/test) 主对话显式（@name) LLM 自动（description 匹配）
上下文 主对话（无隔离） 独立上下文（隔离） 主对话内嵌（无隔离）
加载成本 无（命令即执行） 每次 5-15 秒 + 8K tokens 启动 50 + 触发 500 + 按需 200 tokens
适用场景 用户主动的固定操作 需要隔离/工具白名单的复杂角色 LLM 推理该用的能力
复用方式 .claude/commands/*.md .claude/agents/*.md .claude/skills/*/SKILL.md

常见触发词的设计模式

description 字段写"何时触发"是核心命题、具体怎么写"触发词"有 3 种模式：

模式 1：动词+对象（sync / generate / review / audit)

适合"做某事"的明确能力。正例：description="Sync CHANGELOG.md from git commits when user says '更新 changelog' / 'sync changelog' / 'release notes'."

动词 + 对象 + 触发词、Claude 看到"changelog" / "release notes" 这种关键词就匹配。

模式 2：工作流阶段（commit 前 / merge 前 / release 前）

适合"在某个时机自动做"的能力。正例：description="Run pre-commit security audit. Use when user is about to commit, push, or merge."

这种 Skill 通常和 Hook 配合——Hook 在 commit 前自动调起、Skill 给出审计报告。

模式 3：任务类型（写测试 / 修 bug / 部署）

适合"按任务分类"的能力。正例：description="Generate unit tests for new functions. Use when user adds new code without tests or says 'write tests' / '补测试' / 'add coverage'."

3 种模式的核心都是"动词 + 时机/对象 + 触发词"三件套。反面是只写"做什么"——Claude 看完不知道"用户什么时候需要"我、触发率 = 0。

触发词模式 正例 description 反例 description 反例后果
动词+对象 Sync CHANGELOG.md from git commits. Use when user says '更新 changelog' / 'release notes'. A changelog generator 描述"做什么"、触发率 = 0
工作流阶段 Run pre-commit security audit. Use when user is about to commit, push, or merge. Audits code 无触发时机、啥时候都用不上
任务类型 Generate unit tests for new functions. Use when user adds new code without tests or says '补测试'. Writes tests 太短、任何场景都"匹配"

Skills 的"加载成本"与"省成本"

Skills 在 3 个层级的 token 成本：

第 1 层：frontmatter 几十行（几十到几百 tokens)——Claude 启动时全量加载、每个 Skill 都看到。这层成本是"固定开销",Skills 多起来会累积。控制：frontmatter 控制在 5-10 行（主要就是 description）。

第 2 层：SKILL.md 正文几百行（几百到几千 tokens)——description 匹配时整段加载。这层成本是"触发时开销"、只有匹配上的才加载。控制：SKILL.md 正文控制在 100-200 行、超过拆 references/。

第 3 层：references/ 深层引用几千行——按需加载、Claude 实际需要时再读。这层成本是"按需开销"、大多数 Skill 几乎不触发这一层。控制：references/ 下放详细文档、API 参考、边界 case。

3 层叠加、Skills 比每次手动调 SubAgent 节省 50% token——因为 SubAgent 每次都把 system prompt + 上下文全量加载、Skills 只在匹配时加载需要的部分。这就是"渐进式披露"的工程价值。

---
name: sync-changelog
description: Update CHANGELOG.md from git commits since the last release. Use when user says "更新 changelog" / "sync changelog" / "release notes" or before a release tag.
license: MIT
allowed-tools: Read, Edit, Bash
---

# sync-changelog: 从 git commits 同步 CHANGELOG

## 快速参考
1. 读 git log --oneline -50 (取最近 50 个 commit)
2. 按 Conventional Commits 分类
3. 追加到 CHANGELOG.md 的 [Unreleased] 段
4. 如果 [Unreleased] 段已发布,新建 [版本号] 段

## 详细步骤
### 1. 读 git log
- `git log --oneline -50 --pretty=format:"%h %s"`
- 如果是 monorepo:`git log --oneline -50 -- `
- 如果 commit 多于 50,加 `--since="3 months ago"`

### 2. 分类(Conventional Commits)
- feat: 新功能
- fix: bug 修复
- refactor: 重构(无功能变化)
- perf: 性能优化
- docs: 仅文档
- test: 仅测试
- chore: 杂项(构建/CI 等)

### 3. 追加到 CHANGELOG.md
- 找到 [Unreleased] 段(没有则创建)
- 按子标题分类追加:### feat / ### fix / ### refactor
- 每条带 commit hash(用反引号包起来)

### 4. 处理已发布段
- 如果上一个版本已发布(版本号 + 日期),新建 [Unreleased] 段
- 读 package.json / pyproject.toml 拿当前版本号

## 边界 case
- 仓库没 CHANGELOG.md: 询问用户是否要初始化(用 ask 机制)
- commit 不规范(无 Conventional Commits 前缀):归到 "### other" 段
- 同一个 commit 涉及多类别:归到主要类别(看 src 变化还是 docs 变化大)
- 已发布版本的 changelog 被改:拒绝并提示"已发布版本不可改"

## 反例
- ❌ 把所有 commit 拼成一段散文(应该按类别分小标题)
- ❌ 跳过分类直接追加(读者找不到自己关心的类别)
- ❌ 修改已发布版本的 changelog(应该新建版本段)
- ❌ 在 [Unreleased] 段用未来日期(应该用 placeholder 日期)

## 深层引用
- Conventional Commits 规范:见 [references/conventional-commits.md](references/conventional-commits.md)
- CHANGELOG 模板:见 [references/changelog-template.md](references/changelog-template.md)
- 完整历史 commit 的 changelog 生成(>50 commits):见 [references/bulk-changelog.md](references/bulk-changelog.md)

│   └── 边界 case (50-100 行)   # 第 2 层:触发时加载
└── references/                 # 选读,按需加载
    ├── conventional-commits.md  # Conventional Commits 完整规范
    ├── changelog-template.md    # CHANGELOG.md 模板
    └── bulk-changelog.md        # 批量 changelog 生成(>50 commits)

# Token 成本对比(假设一个对话需要 sync-changelog):
#   全量加载 SKILL.md:           5000 tokens(1 次性)
#   渐进式披露:                  50 (frontmatter) + 500 (正文) + 200 (按需 ref) = 750 tokens
#   节省:                        5000 - 750 = 4250 tokens(85% 节省)
#
#   对比 SubAgent 跑同样任务:     10000 tokens (system prompt 8000 + 上下文 2000)
#   节省:                        10000 - 750 = 9250 tokens(92% 节省)

# 3 层叠加,Skills 比 SubAgent 节省 50%-90% token 成本

⚠️ 常见坑

⚠️ description 写"做什么"而不是"何时触发"（触发率 = 0)

最常见也最隐蔽的错误：Skill 的 description 写"A changelog generator"（描述"做什么"）而不是"Update CHANGELOG.md from git commits when user says '更新 changelog' / 'release notes' or before a release tag"（描述"何时触发"）。前者让 Claude 不知道"用户什么时候需要"我、触发率基本为 0；后者让 Claude 一看到"changelog" / "release notes"关键词就自动加载、触发率 80%+。判断标准：把 description 拿给一个新来的 AI 工程师、问"你在什么情况下会用这个 Skill?"——如果他答不上来、就是写错了。和 SubAgent 的 description 是同一个逻辑、务必写"何时触发"。

⚠️ SKILL.md 一次塞 1000 行（上下文爆炸）

新人最常犯的"渐进式披露失效"错误：把所有详细文档、API 参考、边界 case 全塞进 SKILL.md 一个文件、一行 1000+。结果是：每次 Skill 触发都把 1000 行加载到上下文、token 成本巨大、而且 Claude 在 1000 行里"找"自己需要的内容也很慢。修正：用 references/ 子目录分层——SKILL.md 控制在 100-200 行（快速参考 + 详细步骤 + 核心边界 case)、详细文档放 references/ 下、SKILL.md 里用"详见 references/xxx.md"引用。判断标准：SKILL.md 超过 300 行就该拆。

⚠️ 把 SubAgent 的任务写成 Skill（角色和能力混了）

常见的设计错位：用户想要"code-reviewer"——一个需要独立上下文 + 工具白名单的审查角色、结果被写成了 Skill。Skill 没有独立上下文、审查时的噪声会污染主对话；没有工具白名单、审查完顺手"优化"了代码就完了。修正：有"独立角色"性质的任务用 SubAgent、有"渐进披露"性质的能力用 Skill。判断标准：这个任务"需要隔离上下文吗?" / "需要配工具白名单吗?" / "需要可并行吗?"——3 个里任一是、用 SubAgent；都不是、用 Skill。

⚠️ Skills 之间 description 重叠（LLM 不知道该选哪个、触发混乱）

项目里同时有 5 个 Skill,description 都提到"测试"——Claude 看到"补测试"时不知道该用 test-writer / test-runner / test-fixer 哪个、触发混乱。修正：每个 Skill 的 description 必须"互斥"、关键词不要重复。test-writer 的 description 里只说"写测试"、test-runner 的 description 里只说"跑测试"、test-fixer 的 description 里只说"修测试",3 者关键词不重叠。判断标准：2 个 Skill 的 description 里搜得到同一关键词（超过 3 个） = 重叠、改其中之一的触发词。

💡 一句话备忘

Skills 是 Claude Code 的"自动能力包":description 写"何时触发"决定触发率、frontmatter 决定启动成本、3 层渐进式披露决定运行成本——9 处细节叠加才能让 LLM 该加载时加载、不该加载时不加载。
