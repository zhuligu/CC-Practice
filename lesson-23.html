📖 详细内容

Agent SDK 是什么？为什么需要它？

前 22 讲我们学的所有扩展机制——SubAgent、Skills、Hooks、MCP、Tools、Rules、Headless——都是"配置式"的：在 .claude/ 目录里写配置，由 Claude Code 加载后使用。这种方式适合"开发者用 Claude Code"——人启动 Claude、Claude 跑任务、人看输出。

但有些场景需要"应用集成 Claude Code"——Web 服务提供 chat API、CLI 工具自动化、数据 pipeline 调用 Claude 处理任务。这些场景要求"编程式"调用：把 Claude Code 的能力当作 Python 函数，被其他代码调用。

Agent SDK 就是为这种场景设计的：把 Claude Code 的能力拆解为可编程接口。

SDK 的 2 个核心 API

API 1：query() 函数——核心入口，接受 prompt + options，返回消息流（异步 generator）。用法：async for msg in query(prompt, options): ...。

API 2：ClaudeCodeOptions 类——配置 query() 行为，11 个字段（allowed_tools / system_prompt / cwd / mcp_servers / max_turns 等）。

这 2 个 API 构成了 SDK 的主体。SDK 还提供 4 类消息类型（Assistant / User / System / Result）用于处理 Claude 的输出。

SDK 的 4 个适用场景

场景 1：Web 服务——Flask / FastAPI 接入 SDK，提供 chat API，用户通过 HTTP 调用 Claude。

场景 2：CLI 工具——把 Claude Code 集成到 CLI，程序员在终端调用 claude-code 跑任务。

场景 3：数据 pipeline——Airflow / Prefect / Dagster 调度 SDK，做数据批处理或跑分析任务。

场景 4：嵌入式应用——把 Claude Code 集成到 IDE 插件、编辑器或桌面应用。

这 4 个场景都是"程序调用 SDK"，而不是"人启动 Claude"。SDK 把 Claude Code 的能力"暴露"为 Python API，供任何应用集成。

SDK vs MCP 的关系

SDK 是"用 Claude Code 的能力"——query() 调起 Claude 推理，由 Claude 跑任务。SDK 站在"调用者"一侧。

MCP 是"用 Claude Code 的工具"——MCP server 把工具暴露给 Claude 调用。MCP 站在"工具提供"一侧。

SDK 调 Claude，MCP 扩展 Claude 工具，二者正交：SDK 可以 + MCP（把 server 加载到 options.mcp_servers），MCP 也可以 + SDK（server 启动后 Claude 用 SDK 调用）。

SDK + MCP 协同示例：Web 服务用 SDK 跑 Claude → Claude 通过 MCP server 调用 GitHub / 数据库 → SDK 接收结果 → 返回 HTTP 响应。

同步 vs 异步

SDK 异步优先——query() 是 async generator，需要用 async for 消费消息。

采用异步的原因：Claude 推理是 IO 密集型（网络请求 + 工具调用），异步既能避免阻塞，也支持高并发（单个进程跑多个 query）。

同步包装：如果你的代码是同步的（不是 async 函数），可以用 asyncio.run(query(...)) 进行包装。

异步 vs 同步：异步适合 Web 服务（高并发）、数据 pipeline（批处理）；同步适合简单 CLI 工具（一次性任务）。

ClaudeCodeOptions 完整配置

ClaudeCodeOptions 类是 query() 的配置项，11 个字段控制 Claude 的行为。

完整配置见后面的"ClaudeCodeOptions 完整配置"代码块。

这 11 个配置项中，最常用的有 5 个：

配置 1：allowed_tools——限制 Claude 能调用的工具（白名单）。生产环境必须收窄，避免 Claude 跑 rm -rf 这类危险命令。

配置 2：system_prompt——自定义系统提示（覆盖默认）。多用户共用 SDK 时，每个请求应该有独立的 system_prompt。

配置 3：cwd——Claude Code 的工作目录（默认当前目录）。SDK 跑在服务里时，要显式指定 cwd，避免文件路径混乱。

配置 4：mcp_servers——加载 MCP server（把 .mcp.json 的内容传进来），让 SDK 集成 Claude + MCP 一起用。

配置 5：max_turns——限制 Claude 推理轮次（默认 25）。防止 Claude 死循环、避免影响性能。

这 5 个常用配置覆盖 80% 的场景。其他 6 个配置项（permission_mode / model / resume / extra_args / settings / env）在高级场景使用。

配置项的"工程定位"

每个配置项都对应一个工程问题：

• allowed_tools 解决"Claude 跑危险命令"的问题。

• system_prompt 解决"不同用户要不同 prompt"的问题。

• cwd 解决"SDK 跑在服务里路径混乱"的问题。

• mcp_servers 解决"SDK 要用 MCP 工具"的问题。

• max_turns 解决"Claude 死循环"的问题。

5 个工程问题对应 5 个配置项，一一对应，设计清晰。

消息分类处理：AssistantMessage / UserMessage / SystemMessage / ResultMessage

query() 返回的是"消息流"——多条消息，需要按类型分别处理。SDK 定义了 4 类消息。

完整处理代码见后面"消息分类处理完整代码"代码块。

4 类消息

类型 1：AssistantMessage（Claude 的回复）——Claude 推理后输出的文本或工具调用。例：Claude 说"让我读这个文件" → AssistantMessage(content="...", tool_calls=[...])。

类型 2：UserMessage（工具结果）——Claude 调用工具后的结果（从 SDK 角度看是"用户消息"，因为 Claude 是"用户"在用工具）。例：Read 工具返回文件内容 → UserMessage(tool_results=[...])。

类型 3：SystemMessage（系统事件）——SDK 内部事件（初始化、hook 触发、工具调用通知等），一般用于调试。

类型 4：ResultMessage（任务结果）——任务结束时的元数据，包含以下字段：

• result（最终输出文本）

• duration_ms（总耗时）

• duration_api_ms（API 调用耗时）

• num_turns（轮次）

• total_cost_usd（费用，美元）

• session_id（会话 ID）

这 6 个字段用于监控和优化。

消息类型 内容 来源 处理方式 元数据
AssistantMessage Claude 的回复 Claude 推理 累积到 final_output / 实时打印 content（文本/工具调用）
UserMessage 工具结果 SDK 注入 一般不用手动处理 content（工具结果）
SystemMessage 系统事件 SDK 内部 调试时打印 subtype（事件类型）
ResultMessage 任务结果 SDK 注入 提取费用 / 轮次、上报监控 cost / turns / duration / session_id

处理循环

处理循环从 query() 流里读取消息，再按类型分发：

1. 遇到 AssistantMessage → 累积到最终输出，或实时打印。

2. 遇到 UserMessage → 处理工具结果（一般不用手动处理，Claude 自己用）。

3. 遇到 SystemMessage → 调试时打印。

4. 遇到 ResultMessage → 提取费用 / 轮次 / 时长，记录到日志或上报监控。

这 4 类消息构成完整的处理循环，SDK 的用法非常清晰。

ResultMessage 元数据的重要性

ResultMessage 包含费用（美元）和轮次，这两个字段决定了"这个 Agent 跑得多贵 / 多复杂"。生产环境必须读取这些字段，用于：

• 成本监控（每月花了多少）。

• 性能分析（平均轮次 / 耗时）。

• 异常告警（单次跑 > $1 触发告警）。

• 优化决策（轮次过多说明 prompt 不好，需要优化）。

不读 ResultMessage = 跑 Claude 不计成本 = 烧钱。

编程式 vs Headless 对比

第 21 讲我们学了 Headless 模式（claude -p 跑任务），本讲学 SDK（编程式调用）。两者都能"非交互跑 Claude"，但工程定位不同。

Headless 模式："命令行跑一次性任务"——CI / cron / 批处理场景跑 Claude，任务结束即退出。

SDK："集成到应用中多次调用"——Web 服务、CLI 工具、数据 pipeline，把 Claude 集成到代码里。

两者的核心区别：Headless 是"进程级别的一次性调用"，SDK 是"函数级别的多次调用"。

SDK 的 4 个优势

优势 1：多轮——SDK 可以跑多次 query()（每次新会话或 resume 旧会话），Headless 每次都是新进程。

优势 2：嵌入到任何应用——SDK 把 Claude 集成到 Flask / FastAPI / Django 等任意框架，Headless 只能 CLI。

优势 3：与现有代码无缝集成——SDK 是 Python 函数，可以和数据库 / Redis / 业务逻辑一起使用；Headless 是子进程，集成成本较高。

优势 4：控制流更细——SDK 可以拿到每条消息（4 类消息）并实时处理；Headless 只能看到最终 stdout。

这 4 个优势让 SDK 适合"应用集成"场景，Headless 适合"脚本自动化"场景。

SDK vs Headless 选择

选择 1：CI / cron / 一次性脚本 → Headless（claude -p）。

选择 2：Web 服务 / 多用户系统 / 与业务逻辑集成 → SDK。

二选一，根据场景决定。

维度 编程式（SDK） Headless 模式
集成方式 Python 函数调用 命令行（子进程）
调用次数 多次（可以 resume） 一次性（每次新进程）
适用场景 Web 服务 / CLI 工具 / pipeline CI / cron / 一次性脚本
控制流 细（4 类消息流） 粗（只看到最终 stdout）
部署 嵌入应用（Flask / FastAPI） 单独 CI 步骤
调试 Python 日志 / 异常 / traceback CI 日志 / 进程退出码

#!/usr/bin/env python3
# message_handling.py
# 4 类消息分类处理 + ResultMessage 元数据读取
import asyncio
from claude_code_sdk import (
    query, ClaudeCodeOptions,
    AssistantMessage, UserMessage, SystemMessage, ResultMessage
)

async def main():
    options = ClaudeCodeOptions(
        allowed_tools=["Read", "Grep", "Bash(git:diff)"],
        max_turns=10
    )

    final_output = ""
    total_cost = 0.0
    total_turns = 0

    async for message in query(prompt="分析这次 PR 的代码", options=options):
        # 类型 1: AssistantMessage（Claude 的回复）
        if isinstance(message, AssistantMessage):
            for block in message.content:
                if hasattr(block, "text"):
                    final_output += block.text
                    print(f"💬 Claude: {block.text}", end="", flush=True)
                elif hasattr(block, "name"):
                    # 工具调用
                    print(f"\n🔧 Claude 调用工具: {block.name}({block.input})")

        # 类型 2: UserMessage（工具结果）
        elif isinstance(message, UserMessage):
            for result in message.content:
                if result.is_error:
                    print(f"\n❌ 工具错误: {result.content}")
                else:
                    print(f"\n✅ 工具结果: {str(result.content)[:200]}...")

        # 类型 3: SystemMessage（系统事件，调试用）
        elif isinstance(message, SystemMessage):
            print(f"\n⚙️  系统事件: {message.subtype}")

        # 类型 4: ResultMessage（任务结果 + 元数据）
        elif isinstance(message, ResultMessage):
            total_cost = message.total_cost_usd
            total_turns = message.num_turns
            print(f"\n\n📊 任务结果:")
            print(f"  最终输出: {message.result[:200]}...")
            print(f"  耗时: {message.duration_ms}ms (API: {message.duration_api_ms}ms)")
            print(f"  轮次: {message.num_turns}")
            print(f"  费用: ${message.total_cost_usd:.4f}")
            print(f"  会话 ID: {message.session_id}")

    # 上报监控
    await report_to_monitoring(
        cost=total_cost,
        turns=total_turns,
        output=final_output
    )

async def report_to_monitoring(cost: float, turns: int, output: str):
    """上报监控(生产环境推到 Prometheus / Datadog)"""
    print(f"\n📈 上报: cost=${cost:.4f}, turns={turns}, output_len={len(output)}")

asyncio.run(main())

# === 4 类消息处理总结 ===
# AssistantMessage  累积到 final_output / 实时打印
# UserMessage      一般不用手动处理(Claude 自己用)
# SystemMessage    调试时打印
# ResultMessage    提取费用 / 轮次 / 时长,记录 + 上报

# === ResultMessage 元数据的重要性 ===
# cost / turns / duration 决定"这个 Agent 跑得多贵 / 多复杂"
# 生产环境必须读,用于:
# - 成本监控(每月花了多少)
# - 性能分析(平均轮次 / 耗时)
# - 异常告警(单次 > $1 触发告警)

async def code_review_agent(pr_diff: str):

    options = ClaudeCodeOptions(

        1. 按严重程度分类问题(🔴 严重 / 🟡 中等 / 🟢 建议)
        2. 每条问题指出:文件:行号 + 问题描述 + 修复建议
        3. 输出 markdown 报告""",
        # 限制轮次
        max_turns=15,
        # 指定 cwd
        cwd="/Users/me/projects/myapp"
    )

    final_report = ""
    async for msg in query(
        prompt=f"请审查以下 PR diff:\n```\n{pr_diff}\n```",
        options=options
    ):
        from claude_code_sdk import AssistantMessage
        if isinstance(msg, AssistantMessage):

                if hasattr(block, "text"):
                    final_report += block.text

from flask import Flask, request, jsonify

app = Flask(__name__)

@app.route("/chat", methods=["POST"])
async def chat_api():
    """HTTP 端点:接收用户消息,返回 Claude 响应"""
    user_message = request.json.get("message", "")
    user_id = request.json.get("user_id", "anonymous")

    # 关键 1:独立 system_prompt(多用户隔离)
    options = ClaudeCodeOptions(
        # 关键 2:异步 + 收窄权限
        allowed_tools=["Read", "Grep", "Glob"],
        # 关键 3:每个用户独立 system_prompt
        system_prompt=f"你是助手,当前用户 ID: {user_id}。回答简洁。",
        # 关键 4:限制轮次
        max_turns=5
    )

    final_text = ""
    cost = 0.0
    async for msg in query(prompt=user_message, options=options):
        from claude_code_sdk import AssistantMessage, ResultMessage
        if isinstance(msg, AssistantMessage):
            for block in msg.content:
                if hasattr(block, "text"):
                    final_text += block.text
        elif isinstance(msg, ResultMessage):
            # 关键 5:ResultMessage 上报(费用 / 轮次监控)
            cost = msg.total_cost_usd
            # 推到监控(略)
            print(f"📊 用户 {user_id} 花了 ${cost:.4f}")

    return jsonify({"response": final_text, "cost": cost})

⚠️ 常见坑

⚠️ 忘了配置 allowed_tools（SDK 默认能跑所有工具，生产环境必须收窄白名单）

"SDK 默认全工具"陷阱：SDK 默认 allowed_tools=None（允许所有工具），生产环境跑 SDK 时若没配 allowed_tools，Claude 就能跑 rm -rf、curl | sh 等危险命令。修正：必须配 allowed_tools 白名单——只允许业务需要的工具（如 Read / Grep / Glob 等）（Read / Grep / Glob 等）。判断标准：你的 SDK options 里有 allowed_tools 吗？没有的话，补上白名单。

⚠️ 异步 query() 没用 async for 消费（运行时拿不到结果，函数立即返回）

"async 忘 await"陷阱：query() 是 async generator，必须用 async for 消费。如果在同步函数里直接调用 result = query(prompt, options) 拿到的只是 async generator 对象（不是结果），遍历它也拿不到消息。修正：用 async for 消费；或者用 asyncio.run() 包装。判断标准：你的代码里有 async for 吗？没有的话，加上 async for。

⚠️ ResultMessage 元数据没读（费用 / 轮次 / 时长没监控，无法优化成本）

"不计成本"陷阱：跑 SDK 不读 ResultMessage 里的 cost / turns / duration，跑 Claude 不计成本。一个月下来发现花了几千美元，却无从下手优化。修正：必须读 ResultMessage，记录到日志或上报到监控（Prometheus / Datadog）。设置告警阈值（单次 > \$1 触发告警 / 每月 > \$500 触发优化）。判断标准：你的 SDK 跑了多少次、每次 cost 多少，能回答吗？不能的话，补上监控。

⚠️ 系统 prompt 没隔离（多用户共用一个 SDK 实例，提示词互相干扰，每个请求应独立 system_prompt）

"多用户 prompt 污染"陷阱：Web 服务用 SDK 提供 chat API、所有用户共用一个 ClaudeCodeOptions（系统 prompt 固定），导致用户 A 的对话历史影响用户 B（因为 Claude 上下文是共享的）。修正：每个请求独立 system_prompt——根据用户 ID / 角色 / 场景生成不同 prompt，每次 query() 都新建 options。判断标准：你的 SDK 每个请求的 system_prompt 独立吗？是根据用户 ID / 角色生成的吗？不是的话，改成独立 prompt。

💡 一句话备忘

Agent SDK 把 Claude Code 的能力拆解为可编程接口——query() 函数 + ClaudeCodeOptions 11 个配置项 + 4 类消息流（AssistantMessage / UserMessage / SystemMessage / ResultMessage），把 Claude Code 集成到任何应用（Web / CLI / pipeline），实现从「配置式」到「编程式」的升级。
