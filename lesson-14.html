Skills 在 AI Agent 生态中的位置

第 10-13 讲我们都在 Claude Code 内部讲 Skills。本讲登高望远、跳出 Claude Code 内部、看 Skills 在整个 AI Agent 生态中的位置。理解生态、才能看清 Claude Code Skills 的独特设计选择。

4 类主流 AI Agent 能力扩展机制

1. GPTs/Actions(OpenAI)——用户主动选功能。每个 Action 是预先定义好的 HTTP API,GPT 在对话中看到用户的话、如果觉得需要就主动调用那个 Action。触发机制：用户主动说 / GPT 推理（混合）、但调用必须先在 GPT 后台注册过。配置方式：JSON + 后台 GUI。生态：OpenAI 闭源。

2. LangChain/Tools——代码层显式调用。开发者用 Python 代码显式调 `tool.run()`,LLM 只能建议调用哪个 tool、实际是否调用由代码控制。触发机制：代码显式（开发者写死在代码里）。配置方式：Python 类 + schema。生态：LangChain 开源。

3. AutoGPT/Skills——任务级触发。每个 Skill 是预先定义好的任务模板,AutoGPT 在跑任务时按模板执行。触发机制：任务触发（任务树中匹配）。配置方式：Python 文件。生态：AutoGPT 开源。

4. Semantic Kernel/Skills（微软）——插件式注册。每个 Skill 是 .NET 类、通过 PluginManager 注册、LLM 在对话中按函数签名调用。触发机制：插件注册（类似 LangChain）。配置方式：C# 类 + YAML。生态：微软。

4 类机制的核心区别在触发机制：

• 用户主动（GPTs 用户层）——用户显式说用 X Action。

• 代码显式（LangChain)——开发者写死调哪个 tool。

• 任务触发（AutoGPT)——任务规划阶段决定调哪个 Skill。

• 插件注册（Semantic Kernel)——LLM 通过函数签名识别调哪个 Skill。

Claude Code Skills 的位置

Claude Code Skills 介于用户主动和代码显式之间、独特在LLM 语义推理触发——Claude 看到用户的话、推理出该用哪个 Skill、不依赖代码层显式注册、也不依赖后台 GUI 配置。这种设计的代价：依赖 description 写得准、触发率不一定 100%。收益：零调用成本、配置轻量、纯文本可 git 跟踪。

Claude Code Skills 的 3 大独特性

3 大独特性是 Claude Code Skills 与其他生态差异化的核心、也是工程设计选择的根因。

特性 1：LLM 语义推理触发

其他生态（除 GPTs 部分）需要代码层显式注册 / 后台配置才能让 LLM 调起某个能力。Claude Code Skills 不需要——你只要写一个 SKILL.md,frontmatter 的 description 写何时触发,Claude 在推理时自动匹配。零代码注册、零后台配置。

代码体现：SKILL.md 的 description 字段是 LLM 推理的索引键、其他生态要么用 JSON schema(OpenAI Actions）、要么用 Python 类签名（LangChain）、要么用插件注册（Semantic Kernel）。Claude Code 的 description 触发是自然语言 + LLM 推理、不是结构化注册。

工程意义：写新 Skill 极轻量——1 个 markdown 文件、5-10 行 frontmatter、描述清楚触发场景、就能用。不需要发包、不需要注册、不需要改 settings.json。

特性 2：渐进式披露（3 层加载、token 节省 98%)

其他生态多采用全量加载或按需全量加载——Skill 触发时把完整定义/能力加载到上下文、不管用不用得上。Claude Code Skills 采用 3 层渐进式披露——frontmatter 50 tokens（启动时全量）+ SKILL.md 2K tokens（触发时加载）+ references/ 按需加载。第 12 讲详细讲过这个架构。

代码体现：.claude/skills/<name>/ 目录结构、SKILL.md 在根、references/ 子目录放深度内容、frontmatter 是 5-10 行的 YAML。其他生态没这个目录结构（OpenAI Actions 是单一 JSON,LangleChain 是 Python 文件）。

工程意义：Skills 数量增加到 50 个也不爆上下文（每个 Skill 只占 50 tokens 启动成本、触发时才加载 2K）。这是 Claude Code Skills 能随便加的核心原因。

特性 3：Markdown 定义（纯文本、可 git 跟踪）

所有 Skills 都是纯 Markdown 文件——SKILL.md + references/*.md、没有二进制、没有编译产物、没有 lock 文件。直接 git 跟踪、直接 PR review、直接 diff。

代码体现：其他生态要么用 JSON(OpenAI Actions)/ Python(LangChain)/ C#(Semantic Kernel)/ YAML(SK 插件）、都不是自然语言。Claude Code Skills 用纯 Markdown + YAML frontmatter、人可读、LLM 可读、git 可 diff。

工程意义：团队协作零摩擦——任何工程师可以改 SKILL.md,PR review 时直接看 diff、不用编译、不用构建、不用发包。

设计模式四象限：频率 × 风险

工程实践需要分类学——把所有 Skills 实践按频率 × 风险两维度分 4 类、每类有推荐配置。这是 Skills 工程的决策树。

第 1 象限：高频低风险

典型场景：review（每次 commit 前）/ lint（每次保存）/ test（每次 push）。这些能力经常被触发、但即使误触也无大碍（只是多跑一次、不会改生产环境）。

推荐配置：普通 Skill（无 disable-model-invocation / 无 Hook 兜底）,description 写何时触发、让 LLM 自动发现。LLM 看到 review / lint 关键词就加载、触发率 80%+ 即可。

第 2 象限：高频高风险

典型场景：deploy（每天多次但每次有后果）/ commit（每次 commit 都改 git 历史）。这些能力经常被触发、误触会有后果（部署到错误环境 / 错误的 commit message 进了主分支）。

推荐配置：加 ask 机制——Skill 加载后不直接执行、而是先 ask 用户确认。Claude 建议用这个 Skill、但用户必须显式确认才执行。这是高频的折中：不阻止自动触发、但增加一道人工确认。

第 3 象限：低频低风险

典型场景：debug-mode（排查问题时用）/ verbose（打印详细日志）/ trace-network（网络调试）。这些能力很少被触发、即使误触也无大碍（只是日志变多）。

推荐配置：普通 Skill（无 disable-model-invocation / 无 Hook 兜底）,description 可以写得广一点（允许 LLM 主动发现）。

第 4 象限：低频高风险

典型场景：rollback（回滚到上一版本）/ db-migrate（数据库迁移）/ purge-cache（清空缓存）/ force-push（强制推送）。这些能力很少被触发、但误触会有灾难性后果（数据丢失 / 生产环境被清空）。

推荐配置：必须配 disable-model-invocation： true + Hook 二次拦截（双保险）。LLM 完全看不到、只有用户主动 /rollback / /db-migrate 才触发；即使有其他路径触发、HW 也拦下危险命令。第 11 讲详细讲过这种双保险配置。

4 个象限的决策心法：

1. 高频 → 优化触发率（LLM 主动发现、description 写准）。

2. 低频 → 优化可见性（用户主动调、加 disable 字段）。

3. 高风险 → 加 ask 机制或 disable 字段（防误触）。

4. 低风险 → 普通配置即可（别过度防御）。

避免两个极端：把所有 Skills 都加 disable 字段（用户每次都得手输命令、反而累）/ 把所有 Skills 都放任 LLM 自动触发（高风险操作误触 = 灾难）。

象限 频率 风险 典型场景 推荐配置
第 1 象限 高 低 review / lint / test 普通 Skill,LLM 主动发现、description 写准
第 2 象限 高 高 deploy / commit 普通 Skill + ask 机制、执行前人工确认
第 3 象限 低 低 debug-mode / verbose / trace-network 普通 Skill,description 可以写广
第 4 象限 低 高 rollback / db-migrate / purge-cache / force-push 必须 disable-model-invocation + Hook 双保险

• Claude Code Skills：LLM 推理触发 / 渐进式披露能力。

Skills 的3 个不做什么

Skills 是 Claude Code 4 种扩展机制之一（Commands / SubAgent / Skills / Hook)、不是万能工具。3 个不做什么边界要清楚。

不做什么 1：Skills 不替代 SubAgent

SubAgent 隔离上下文——审查时主对话的噪声不会污染审查结果。Skill 共享主对话上下文——Skill 加载时、主对话的内容（用户隐私 / 中间状态）都被看到。

什么时候用 SubAgent：需要独立上下文的任务（代码审查 / 数据分析 / 长时间跑的任务）。

什么时候用 Skill：LLM 推理该用的能力（更新 changelog / 生成 API 文档）。

不做什么 2：Skills 不替代 Commands

Commands 用户主动调——用户显式说用 /<name>。Skill LLM 触发——LLM 看到 description 匹配自动加载。

什么时候用 Command：需要显式用户意图（用户决定何时用哪个）。

什么时候用 Skill：需要LLM 智能发现(LLM 决定何时用哪个）。

不做什么 3：Skills 不替代 Hook

Hook 是底层机制——PreToolUse / PostToolUse 拦截具体工具调用、完全可编程。Skill 是上层能力——描述做什么、由 LLM 推理决定是否调起。

什么时候用 Hook：需要硬约束（危险命令拦截 / 自动备份 / 强制 lint）。

什么时候用 Skill：需要智能触发(LLM 该用就用、不该用就不触发）。

3 个不做什么的本质：4 种扩展机制有明确的职责边界——Commands（用户层）/ SubAgent（角色层）/ Skills（能力层）/ Hook（机制层）、各管一摊、不要混用。混用的代价是职责重叠 / 改一处忘一处 / 触发混乱。

Skills 工程实践的 4 个长期习惯

4 个长期习惯是 Skills 工程的最佳实践基线、任何团队/项目都应该坚持。

习惯 1：每个 Skill 都有 description

写何时触发不写做什么。description 是 LLM 推理的索引键、写错 = 触发率 = 0。第 10 讲详细讲过 description 的写法。

习惯 2：章节控制在 200 行内

超过 300 行就该拆 references/。SKILL.md 章节是主入口,references/ 是深度文档。3 层渐进式披露是 token 经济性的核心（第 12 讲）。

习惯 3：危险操作加 disable-model-invocation + Hook 双保险

任何低频高风险操作（rollback / db-migrate / force-push）必须配双保险（LLM 看不到 + Hook 拦截危险命令）。单层防御不够、双保险才能兜底（第 11 讲）。

习惯 4：进 git + 配 PR review

Skills 是工程资产、不是个人草稿。所有修改必须进 git、所有变更必须 PR review。这保证团队用的 Skills 是一致的、可追溯的、可回滚的。

4 个习惯的检查清单（可作为 PR review 模板）：

1. [ ] 每个 Skill 都有 description（写何时触发不是做什么）。

2. [ ] SKILL.md 章节控制在 200 行内（超过 300 行拆 references/）。

3. [ ] 危险操作加 disable-model-invocation： true + Hook 二次拦截。

4. [ ] 进 git + 配 PR review（团队资产、不是个人草稿）。

PR review 时按这个清单逐项检查、任何一项不合格打回。

    - 必须配 disable-model-invocation: true(LLM 看不到)
    - 必须配 Hook 二次拦截危险命令
    - 只有用户主动 /rollback / /db-migrate 才触发
  示例:
    ---
    name: rollback
    description: NOT-USED-BY-MODEL
    disable-model-invocation: true
    ---
    # + .claude/hooks/deny-extra-dangerous.sh
    # 拦截 git reset --hard / kubectl rollout undo 等

📄 第 14 讲配套：Claude Code Skills 3 大独特性的代码体现（LLM 推理触发 / 渐进式披露 / Markdown 定义）

# === 独特性 1:LLM 语义推理触发 ===
# Claude Code Skills 的 description 是 LLM 推理的"索引键"
# 不需要代码注册、不需要后台配置,纯自然语言

# 正面:description 写"何时触发"
---
name: sync-changelog
description: Update CHANGELOG.md from git commits. Use when user says "更新 changelog" / "release notes" / "CHANGELOG 同步".
---

# 反面:description 写"做什么"
---
name: changelog-generator
description: A changelog generator
# → LLM 不知道何时触发,触发率 = 0
---

# === 独特性 2:渐进式披露(3 层加载) ===
.claude/skills/sync-changelog/
├── SKILL.md                       # 第 2 层:章节(2K tokens,触发时加载)
│   ├── frontmatter (50 tokens)    # 第 1 层:目录页(启动时全量)
│   ├── 快速参考 (5-10 行)
│   ├── 详细步骤 (30-50 行)
│   └── 边界 case (50-100 行)
└── references/                    # 第 3 层:附录(按需加载)
    ├── conventional-commits.md    # 1K tokens
    └── changelog-template.md      # 0.5K tokens

# Token 成本:
# - 启动时:50 tokens(frontmatter)
# - 触发时:2K tokens(SKILL.md)
# - 按需:0.5-1K tokens(references)
# - 总计:2.55K(对比全量 30K,节省 91%)

# === 独特性 3:Markdown 定义(纯文本) ===
# 整个 Skills 体系就是 Markdown + YAML:
# - SKILL.md:自然语言正文
# - frontmatter:YAML 元数据
# - references/*.md:深度文档

# 没有 JSON / Python / C#,没有编译产物,没有 lock 文件
# 直接 git 跟踪:
git add .claude/skills/sync-changelog/
git commit -m "feat(skill): add sync-changelog skill"
git push origin main
# 团队 PR review 时直接看 Markdown diff,无歧义

📄 第 14 讲配套：Skills 工程实践的 4 个习惯检查清单（可作为 PR review 模板）

# Skills PR Review 模板

## 提交新 Skill / 修改现有 Skill

### 习惯 1:每个 Skill 都有 description
- [ ] description 写"何时触发",不写"做什么"
- [ ] description 在 1-2 句话内(不超过 100 字)
- [ ] 包含 2-3 个触发词(中英文都列)

### 习惯 2:章节控制在 200 行内
- [ ] SKILL.md 主体 < 200 行
- [ ] 超过 300 行 → 拆 references/
- [ ] 3 段式结构(快速参考 / 详细步骤 / 边界 case)

### 习惯 3:危险操作加双保险
- [ ] 低频高风险操作(rollback / db-migrate / force-push)加 disable-model-invocation: true
- [ ] 配套 Hook 拦截危险命令(.claude/hooks/deny-extra-dangerous.sh)
- [ ] 测试:即使 LLM 误触发,HW 也能拦截

### 习惯 4:进 git + 配 PR review
- [ ] .claude/skills/<name>/SKILL.md 在 git 跟踪中
- [ ] 任何修改都有 PR + reviewer
- [ ] 团队 Skills 库统一管理(不私自改)

### 反例检查(任何一项命中 → 打回)
- ❌ description 写"做什么"而不是"何时触发"
- ❌ SKILL.md 1000+ 行(违反渐进式披露)
- ❌ 危险操作只有 disable 没有 Hook(单层防御)
- ❌ Skills 没进 git(个人草稿,不是团队资产)

⚠️ 常见坑

⚠️ 把 Skills 当万能工具（应该和 SubAgent / Commands / Hook 配合、各有边界）

新人最常见的过度依赖：以为 Skills 能做所有事、于是把所有能力都写成 Skill。结果——需要隔离上下文的审查任务用 Skill（上下文被污染）/ 需要用户主动的精确控制用 Skill(LLM 自由发挥、误触发）/ 需要硬约束的危险操作只用 Skill（没配 Hook 兜底）。修正：Skills 是 4 种扩展机制之一、各管一摊——Commands（用户层主动调）/ SubAgent（角色层隔离上下文）/ Skills（能力层 LLM 推理触发）/ Hook（机制层硬约束）。判断标准：这个任务属于哪一层?层对了、选对应机制；层错了、选哪个都不对。

⚠️ 不写 description(LLM 无法触发、Skill 退化成死文档)

描述缺失的隐形坑：有些团队的 Skill 模板规定必须有 description、但实际写 SKILL.md 时只写了快速参考 / 详细步骤 / 边界 case三段、frontmatter 里的 description 字段是空的或写做什么(A changelog generator）。结果——LLM 不知道何时触发、Skill 永远不会被自动加载、退化成死文档（只在用户手动翻 SKILL.md 时才有用）。修正：description 必须写何时触发 + 触发词、1-2 句话、1-100 字。判断标准：LLM 看到 description 后能回答用户在什么情况下需要调起我?——能答、正确；答不了、打回。

⚠️ 章节文件 1000+ 行（违反渐进式披露,token 爆炸）

伪 3 层、实 1 层的常见陷阱（第 12 讲详述）：目录 + 章节 + 附录 3 个文件都建了、但章节 SKILL.md 1000+ 行、把该放附录的深度内容也塞进去。结果——每次 Skill 触发、1000+ 行一次性加载、加载量 5-10 倍于 3 层方案。修正：章节控制在 200 行内、超过 300 行拆 references/。判断标准：SKILL.md > 300 行 = 该拆了。

⚠️ 危险操作没配双保险（disable-model-invocation + Hook 缺一不可）

单层防御的假安全：给 rollback / db-migrate / force-push 加了 disable-model-invocation： true、以为就安全了。但 disable 字段是LLM 推理层的防御——如果有人绕开 LLM 推理、直接调起 Skill(CLI 传参 / CI 流水线自动调 / 别的 Skill 嵌套调）,disable 就失效了。必须加第二层 Hook 防御——PreToolUse Hook 拦截危险命令。双保险叠加、几乎不可能误执行。判断标准：你的危险操作 Skill 配了 Hook 兜底吗?没配、补上。

💡 一句话备忘

Skills 在 AI Agent 生态中的独特位置是LLM 语义推理触发 + 渐进式披露 + Markdown 定义——3 大独特性叠加形成轻量 + 智能 + 可协作的差异化；4 个长期习惯（description / 章节行数 / 双保险 / git PR）是 Skills 工程的最佳实践基线。
