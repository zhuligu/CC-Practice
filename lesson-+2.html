本文是《Dynamic Workflows 工程化实战》系列文章的上篇。

2026 年 6 月，Anthropic 抛出 Dynamic Workflows——把"编排"从对话搬进代码，让 Claude 现写 harness，把任务拆给一队 Claude 并行去干。这是 Claude Code 工程化在"流程编排"维度的一次跃迁。

本系列分为上下两篇，上篇讲清原理（是什么、怎么跑、解决什么问题、5 种工程范式），下篇讲落地（如何把 Excel 数据分析流水线搬上 Dynamic Workflows，如何沉淀为团队资产）。

一、Dynamic Workflows 到底是什么

1.1 一句话定义

Anthropic 给 Dynamic Workflows 的官方定义只有一行：

A workflow moves the plan into code.
工作流，把计划搬进了代码。

更口语化一些：

Dynamic Workflows = 让 Claude 根据你的目标，现场写一段 JS 编排脚本，由 Runtime 调度数十到数百个子 Agent 并行执行，最后返回收敛后的结果。

关键词三个：

  1. 现场写：不是预定义模板，不是你手搓代码——你只描述目标，Claude 自己写脚本。
  2. 并行执行：Runtime 在本机把子 Agent 撒出去同时干活，最多 16 个并发，单次上限 1000 个。
  3. 收敛返回：不是把中间结果丢给你，而是经过对抗验证后，只把最终答案给到主会话。

1.2 它解决了什么"老大难"

在过去，单 Agent 跑长任务有三个反复出现的失败模式：

失败模式 表现 根因
偷懒（Agentic Laziness） 50 个文件审到 35 个就宣布"干完了" 上下文塞满后注意力稀释，把"差不多"当成"做完"
自夸（Self-Preferential Bias） 让 Claude 验自己的活，它偏向维持自己之前的结论 自己给自己打分，等于"让学生批自己的卷子"
跑偏（Goal Drift） 多轮压缩后，边界要求、约束条件一点点丢失 每次摘要都有损，最后解的根本不是原题

Dynamic Workflows 用一种结构性的方式解决这三件事：

  • 隔离：每个子 Agent 拿一个干净独立的小上下文，没有谁握着整个任务 → 偷懒无处藏。
  • 独立验证：干活的是 A，验活的是 B，互相不共享上下文 → 自夸自然消失。
  • 每个窗口都短：每个 Agent 只盯一件事，长期目标被 Runtime 写死 → 跑偏被摁住。

1.3 和传统多 Agent 编排的本质区别

很多人第一反应是：这不就是加强版的 subagent 吗？

不是。 我们把 Claude Code 已有的几种机制横向拉出来对比：

维度 普通会话 SubAgent Skill Agent Teams Workflow
编排者 用户 主 Claude 逐轮 主 Claude 逐轮 主 Claude 网状协作 JavaScript 脚本
中间结果存放 上下文窗口 回到上下文窗口 回到上下文窗口 队员收件箱+上下文 脚本变量（堆内存）
规模量级 单次会话 一轮派几个 一次一条指令 几个队员长期共事 数十到数百，最多 1000
协作拓扑 串行 星形 链式 网状 树状（fan-out → fan-in）

重点看"中间结果存放"那一行：前四种机制里，中间结果最终都要回到主上下文；只有 workflow 把中间结果从"上下文窗口"搬到了"脚本变量"。

当任务规模大到上下文装不下，前面四种机制都开始吃力，workflow 才是补上那一格。

1.4 一句话定位

Workflow 不是 subagent / skill / team 的替代品，而是补上它们够不到的那一格——"单个 Agent 一次跑不完、中间结果多到上下文装不下"的大任务。

日常 80% 的活照旧使用 subagent / skill；只有当你在写需求时心里冒出一句"这要拆几百个文件分别处理"的时候，workflow 才登场。

二、Dynamic Workflows 的架构与原理解析

2.1 整体运行链路

Dynamic Workflows 的运行链路有 4 个关键节点：

这里藏着最容易被误解的一点：workflow 不是跑在 Anthropic 服务端的什么编排引擎，它就是 Claude Code 在你本机起的一段 JavaScript 脚本，由一个本地 JS 运行时执行。

理解这一点，很多看起来神奇的能力就一下子合理了：

  • 为什么能扛住几百个并发 Agent？ 因为真正在外面循环的是那段不调用模型的 JS。
  • 为什么主 Claude 上下文不会爆？ 主 Claude 拿到的只是 workflow 最后 return 的小对象，中间几百个 Agent 的输出根本没进它的窗口。
  • 为什么中断后能恢复？ 脚本运行进度落到本地，不依赖那条对话的内存状态。
  • 为什么协调成本几乎为零？ 循环、判断、汇总本来就不该让 LLM 来做，让 V8 跑就行。

2.2 8 个基础原语

workflow 脚本是普通 JavaScript，但 Claude Code 在运行环境中注入了 8 个原语。按使用频率分两层：

第一层（结构骨架）

原语 作用
metaworkflow 的身份证，导出 name / description / phases，必须是纯字面量
phase(title)把进度切成大段，只影响 UI 展示，不影响执行顺序
agent(prompt, opts)唯一会调用 LLM 的那一行，雇一个有干净上下文的子 Agent
parallel(thunks)有 barrier 的并发——全部跑完才往下走
pipeline(items, ...stages)无 barrier 的流水线——A 跑到 stage3 时 B 还能在 stage1

第二层（工程能力）

原语 作用
schemaJSON Schema 约束，强制结构化输出，运行时自动校验重试
budgettoken 预算对象，配合 while 写"边花边干"的循环
log进度可见，不是 console.log，输出到 /workflows 视图
args把 workflow 变成参数化模板，存到 .claude/workflows/ 后成为可复用命令
isolation: 'worktree'子 Agent 在独立 git worktree 里跑，避免文件冲突

把第一层掌握就能让 workflow 跑起来；把第二层掌握才能写出生产可用水平。

2.3 5 种工程范式

8 个原语可以组合出形形色色的编排模式，实战中反复出现的就是这 5 种：

范式 1：对抗性验证（Adversarial Verify）

LLM 给出的结果"看似正确实则错误"是高频问题。解法：让 N 个独立 Agent 尝试反驳，多数反驳成功就剔除。

const votes = await parallel([
  () => agent(`尝试反驳：${claim}。如果不确定，默认 refuted=true。`, { schema: VERDICT_SCHEMA }),
  () => agent(`尝试反驳：${claim}。如果不确定，默认 refuted=true。`, { schema: VERDICT_SCHEMA }),
  () => agent(`尝试反驳：${claim}。如果不确定，默认 refuted=true。`, { schema: VERDICT_SCHEMA }),
])
const survives = votes.filter(Boolean).filter(v => !v.refuted).length >= 2

两个细节值得品：

  1. 默认值偏保守——"如果不确定就当 refuted=true"，宁可错杀也不要放过。
  2. 3 个 Agent 跑的是同一个 prompt，但它们的随机性相互独立，所以多数投票本身就是一种降噪。

范式 2：循环直到达标（Loop-until-dry）

面对"代码库里到底有多少 bug"这种规模未知的任务，写不出"跑 N 轮就够"的常量。那就让它跑到没东西可挖为止：

const seen = new Set()
let consecutiveEmpty = 0
while (consecutiveEmpty < 2 && budget.remaining() > 100_000) {
  const result = await agent('找出代码中尚未发现的 bug', { schema: BUGS_SCHEMA })
  const newBugs = result.bugs.filter(b => !seen.has(b.id))
  if (newBugs.length === 0) consecutiveEmpty++
  else { consecutiveEmpty = 0; bugs.push(...newBugs) }
}

退出条件是"连续 K 轮没有新发现"，配合 budget.remaining() 兜底防止跑飞。

范式 3：多视角评审（Judge Panel）

需要做开放性决策（设计方案、文案选型、API 设计）时，让多个 Agent 从不同角度独立提方案，再让一组评委打分。注意提方案和打分严格隔离——提方案的不知道有评委，打分的不知道方案是谁出的。

范式 4：多维度扫描（Multi-modal Sweep）

一个维度一个 Agent，全部并行扫一遍。代码审查就是经典场景：

const DIMENSIONS = [
  { key: 'security',      prompt: '审查安全性：SQL 注入、XSS、硬编码密钥、越权' },
  { key: 'performance',   prompt: '审查性能：N+1 查询、内存泄漏、不必要的重渲染' },
  { key: 'maintainability', prompt: '审查可维护性：代码重复、过长函数、深层嵌套' },
]
const reviews = await parallel(DIMENSIONS.map(d => () =>
  agent(d.prompt, { label: `review:${d.key}`, phase: 'Review', schema: FINDING_SCHEMA })
))

好处：每个 Agent 只关心一件事，prompt 短、噪音小、输出聚焦。

范式 5：Pipeline 默认优于 Barrier

决策规则：默认 pipeline。只有当你确实需要"前一阶段全部结果"才能进下一阶段（去重、汇总、打分、选最优）时，才换 parallel barrier。

为什么这条单独拎出来？因为它直接影响 workflow 的总耗时和成本。多问自己一句"我真的需要等齐吗"，就能省下一大把时间和 token。

2.4 一段最小骨架

export const meta = {
  name: 'review-codebase',
  description: '多角度代码审查',
  phases: [
    { title: 'Discover', detail: '发现问题' },
    { title: 'Verify',   detail: '验证发现' },
  ],
}

phase('Discover')
const findings = await parallel([
  () => agent('从安全角度找问题',       { schema: FINDING_SCHEMA }),
  () => agent('从性能角度找问题',       { schema: FINDING_SCHEMA }),
  () => agent('从可维护性角度找问题',   { schema: FINDING_SCHEMA }),
])

const claims = findings.filter(Boolean).flatMap(r => r.items)
log(`共 ${claims.length} 条待验证发现`)

注意：filter / flatMap 是普通 JS，不消耗任何 LLM token。这是 workflow 相对普通 subagent 模式最关键的差异——主 Claude 此时正在睡觉。

三、Dynamic Workflows 解决的问题类型

3.1 任务规模远大于一次会话能装下的上下文

几百个文件的中间结果往主 Claude 上下文里一塞，注意力立刻被稀释，很快就溢出。workflow 把中间结果存在脚本变量里，主 Claude 最后只拿一个 return 的小对象。

典型场景：

  • 跨整个仓库的代码审计
  • 跨整个服务的大规模 Bug 扫描
  • 海量内容的横向深度研究

3.2 结构高度规则化、可编排的任务

扇出（fan-out）→ 各自跑 → 汇合（fan-in）这个模式被反复使用，模式比内容稳定。

典型场景：

  • 多文件批量翻译
  • 批量生成单元测试
  • 多接口安全审计
  • 全文档批量格式化

3.3 协调本身的算力很便宜的任务

循环 1000 次、把数组 filter 一遍、按文件名分组——这些用 LLM 来做完全是浪费，用一段 JavaScript 跑就行。

典型场景：

  • 排序 / 打分：1000 条工单按严重度排序
  • 去重：1000 个候选文件名去重
  • 分组：1000 个设备按类型分组
  • 索引：把分散在多个文件的内容汇总成索引

3.4 需要对抗性验证的高风险决策

不能只靠模型自信输出结果，必须让结果经过反驳-收敛的过程。

典型场景：

  • 跨服务的方案择优
  • 高风险的代码评审
  • 学术结论的交叉核对
  • 投融资材料的多视角质疑

3.5 Anthropic 官方反复使用的 6 大场景

总结 Anthropic 官方博客里点名的场景，直接拿走就能用：

  1. 迁移与重构——Bun 用 workflow 11 天把 75 万行 Zig 重写为 Rust
  2. 深度研究——/deep-research 内置 workflow：扇出搜索 → 抓取 → 投票 → 综合
  3. 深度验证——对每个事实声明拉独立 Agent 验证 + 验证 Agent 反查
  4. 排序——用 tournament / pipeline pairwise / bucket-rank 替代单次打分
  5. 根因排查——多角度独立假设 + 反驳面板（防自夸）
  6. 大规模 triage——自动分类 + 去重 + 升级处理

四、Dynamic Workflows 实用设置与使用指南

4.1 开启条件

最低门槛：

  • Claude Code v2.1.154 或更高版本
  • 支持平台：CLI、桌面应用、VS Code 扩展、Amazon Bedrock、Google Cloud Vertex AI、Microsoft Foundry

计划可用性：

计划 默认状态 开启方式
Max / Team / API✅ 默认开启直接用
Pro可通过 /config 中"Dynamic workflows"开关开启/config
Enterprise❌ 默认关闭管理员在 Claude Code 设置中开启

4.2 三种触发方式

方式一：关键词触发——在提示词里直接写 workflow：

用 workflow 审计 src/routes/ 下每个 API 端点，检查是否缺少身份验证检查

Claude Code 会高亮显示你输入中的关键词。如果它在你不想触发时启动了，alt+w 可忽略本次触发。

方式二：自动模式 ultracode——让 Claude 自己判断：

/effort ultracode

开启后，Claude 会为会话中每一个实质性任务规划一个 workflow。一个请求可能变成连续几个 workflow：理解 → 变更 → 验证。代价是每个请求使用更多 token、跑更久。日常用 /effort high 即可。

方式三：手动指定——直接说"创建一个工作流"：

创建一个 workflow，帮我把 Bun 从 Zig 移植到 Rust

4.3 运行时的硬约束

在写任何雄心勃勃的方案前，先记住这几条硬约束：

约束 详情
最大并发 Agentmin(16, CPU 核数 - 2)，本机 CPU 决定
单次 workflow 最多 Agent 数1000 个，防止失控循环烧 token
运行时间没有硬上限，但有 budget 兜底
中途用户输入不可，仅权限提示能暂停
脚本本身没有文件系统/Shell 访问，只能通过 agent() 调度 Agent 来读写
meta 必须是纯字面量不能有变量、函数调用、模板插值

一个值得内化的安全细节：workflow 生成的子 Agent 始终以 acceptEdits 模式运行，并继承你的工具允许列表，无论你会话的权限模式是什么。文件编辑在运行内部是自动批准的；不在允许列表中的 shell 命令、网络获取和 MCP 工具仍然会暂停并询问你。在一个长时间无人值守的运行中，提前将 Agent 需要的命令添加到允许列表，否则它会因为等待你而停滞。

4.4 四把成本控制杠杆

  1. 不同阶段路由不同模型：Discover/扫描类用 haiku，写代码用 sonnet，关键决策用 opus。三段式路由能省大约一半 token。
  2. budget.remaining() 兜底循环：所有 while 循环都加预算判断，再加"连续 K 轮无新发现"双保险。
  3. 去重在脚本里做，别让 LLM 做：JS 一行 Set 解决的事，不要交给 Agent。
  4. /workflows 按 p 暂停、按 x 停止：跑偏了立刻停，已完成的 Agent 结果不会丢。

4.5 进度查看与可恢复

进度查看：/workflows 打开一个运行面板，每个阶段、每个子 Agent、每次工具调用和 token 消耗都看得到，还能暂停、跳过卡住的、重试单个 Agent。

断点续传：每次运行有 ID，断了能接着跑——已完成的 Agent 走缓存、只补没干完的。但退出 Claude Code 后再开会重新开始，不要把长时间运行的任务当作能在重启后持久化的任务。

4.6 沉淀、复用与团队共享

保存：在 /workflows 视图里选运行，按 s 保存为命令，存到两个位置之一：

  • 项目级：.claude/workflows/（提交仓库，与克隆它的每个人共享）
  • 个人级：~/.claude/workflows/（每个项目可用，仅本人可见）

之后就能在未来的会话里用 / 触发，与 /deep-research 一起出现在自动补全中。

团队共享：把 JS 文件丢进项目的 .claude/workflows/，像审查任何代码一样在 PR 里审查。.claude/workflows/ 文件夹本质上是团队的编排模式库——你的安全审计模板、你的迁移模板、你的发布前 review。

注意：在 Skill 里分享时，把它当作模板而非死脚本，让 Claude 面对具体任务时自适应，而不是一行不差地重放。

4.7 什么时候不要用

workflow 是研究预览版，不是所有任务都值得烧那么多 token。

判断标准：这个任务，是不是真的需要比"一个上下文窗口"更多的算力？

  • ❌ 不要用：单文件小修、只改一两个文件、你每一步都要拍板的
  • ✅ 值得用：50 个文件的安全审计、上千行的排序打分、跨仓库重构、高风险要独立验证的改动、高复用值得沉淀成模板的流程

经验法则：

场景 选择
简单单文件修改❌ 直接对话
每一步都要你拍板❌ workflow 是无人值守的
多个 Agent 抢同一片文件但边界没拆清❌ 先拆模块再上
跨整个代码库的审计 / 迁移 / 重构✅ 典型场景
高风险决策需要多角度对抗性验证✅ 用范式 1
规模未知、要循环到收敛的探索任务✅ 用范式 2 + budget
一次对话上下文装不下、中间结果海量✅ workflow 的主战场
团队里反复跑的高价值流程✅ 沉淀进 .claude/workflows/

五、将 Dynamic Workflows 思想落地实践项目

workflow 不只是 Claude Code 的特性，它背后的"动态编排"思想可以迁移到任何企业级 Agent 平台。我们看三个典型落地场景，从"参考其思想"到"完整落地一个项目"。

5.1 落地思路：动态编排平台五层架构

要把 workflow 思想迁移到企业项目，至少需要这五层能力：

关键洞察：动态生成解决"个性化"，经验沉淀解决"规模化"——这正是 ToB Agent 平台商业化的关键。

5.2 落地案例：物流行业的多模态运单审核

某物流企业每天有几万张运单需要审核（图片 + 文本 + 结构化字段），传统 OCR + 规则准确率 85%，错审成本高。

Dynamic Workflows 化后：

[Phase 1 Discover] 多视角 Agent 并行
  ├─ 图像识别 Agent 检查运单照片完整性
  ├─ 文本理解 Agent 提取关键字段（重量 / 体积 / 目的地）
  └─ 规则校验 Agent 检查异常（超重 / 违禁品关键词）

[Phase 2 Verify] 对抗性验证
  ├─ 每条疑似异常拉独立 Agent 反驳
  └─ 2/3 多数票决定是否真异常

[Phase 3 Synthesize]
  ├─ 合并三个 Agent 的结构化输出
  └─ 生成可解释的审核报告

收益：准确率从 85% 提升到 96%，每条审核耗时从 8 秒降到 2 秒。

5.3 落地避坑指南

把 workflow 思想迁移到企业项目时，有 4 个常见坑：

  1. 没有 Runtime 兜底——动态编排很容易退化成一段复杂 Prompt。一定要有独立的 Runtime 层管理状态、并发、异常。
  2. 没有验证机制——企业场景不能只靠模型自信输出，必须有"数据完整性 + 工具调用成功 + 多 Agent 结果冲突检测 + 高风险建议人工确认"四道关。
  3. 没有沉淀机制——每次跑完的 workflow 都应该沉淀为可复用模板、行业模板、评估规则，否则只是又一次性的脚本。
  4. 没有成本控制——把"不同阶段路由不同模型 + budget 兜底 + JS 做去重 + 用户中断能力"四把杠杆全用上，否则一次跑飞就可能烧掉一周预算。

写在最后：从"会干活"到"会组织一群人干活"

回头看 agent 工程化路线，动态工作流给出了一个很激进但很优雅的解法：干脆把循环从 LLM 里搬出来，搬到一个无脑、确定性、便宜的 JS 运行时里。LLM 只在 agent() 那一行临时露一面，干完就走。

无论后面 Agent 怎么演化，"把循环搬出 LLM"这个原则会反复出现。它是 agent 工程的一个底层重力。

对企业落地来说，Dynamic Workflows 不是终点，而是起点：

  • 它示范了一种范式——目标驱动的动态编排，复杂任务不应只依赖单个 Agent 连续推理。
  • 它验证了一条路径——脚本化的、可复用的、可版本控制的 AI 编排逻辑，让"AI 写代码给我们用"成为可能。
  • 它指向一个未来——Agent 从"会干活"走向"会组织一群人干活"，从执行者变成 FDE（Forward Deployed Engineer）。

上篇讲完原理、原语与范式，你已经知道 Dynamic Workflows 是什么、怎么跑、能解决什么问题。但这一切真正的复利，要在落地实战中才能兑现——下一讲下篇，会以数据分析师的视角，演示如何把 Excel 数据分析流水线搬上 Dynamic Workflows，并把它沉淀为团队可复用的工程资产。
