本讲的三条主线：

📖 详细内容

5 类原子操作

Claude Code 默认带 6 个核心工具 + 多个 MCP 工具 + 几个交互工具。看似多、实际拆解到操作类型上只有 5 类——读 / 写 / 搜 / 执行 / 交互、5 类覆盖了 Claude 与信息源和操作的所有交互。

类 1：读（Read / Glob)

读 = 把信息从某处拿到 Claude 眼前。

• Read（读文件内容）——输入 file_path、输出文件内容（限 ≤2000 行）。

• Glob（按模式列文件）——输入 pattern（如 *.py)、输出匹配的文件路径列表。Glob 也算读类、因为它从文件系统读文件清单。

读类的特征：从某处（文件 / 文件系统）读信息到上下文。

类 2：写（Write / Edit)

写 = 把 Claude 推理结果落到某处。

• Write（创建或覆盖文件）——输入 file_path + content、创建新文件或覆盖旧文件。

• Edit（精确编辑文件）——输入 file_path + old_string + new_string、把文件里 old_string 替换成 new_string（原子操作）。

写类的特征：把内容落到文件 / 数据库 / 外部系统。

类 3：搜（Grep / Glob)

搜 = 在大量信息里找匹配的部分。

• Grep（按内容搜文件）——输入 pattern + path、输出包含 pattern 的行（带文件路径 + 行号）。

• Glob（按文件名搜）——和读类重叠、Glob 既算读也算搜。

搜类的特征：不读全部、只读匹配的、降低上下文消耗。

类 4：执行（Bash)

执行 = 让 Claude 跑命令。

• Bash（跑 shell 命令）——输入 command、跑任意 shell 命令、返回 stdout / stderr / exit_code。

执行类的特征：启动子进程、跑命令。Claude Code 99% 的动作都靠 Bash 完成——跑 git / pytest / curl / npm / python / docker 等。

类 5：交互（AskUserQuestion / WebFetch / WebSearch)

交互 = 和用户或外部世界双向沟通。

• AskUserQuestion（问用户问题）——Claude 在决策点向用户提问、用户提供选项。

• WebFetch（抓 URL 内容）——输入 url、返回 HTML 转 Markdown 的内容。

• WebSearch（搜网络）——输入 query、返回搜索引擎结果。

交互类的特征：不只是单向读或单向写、是双向的——AskUserQuestion 是问用户，WebFetch / WebSearch 是问互联网。

5 类操作加起来 = Claude 能读信息（读 / 搜 / 交互-外部）+ 写信息（写）+ 执行动作（执行）+ 问用户（交互-用户）。这是一个 AI Agent 的完整能力图。

工具涌现：组合产生复杂能力

5 类原子操作 → 十几个原语工具、看似简陋、但工具涌现让它们组合出无限可能。

涌现的本质

涌现（emergence)：小单元组合产生复杂能力、复杂能力不需要专门工具。

类比：水的 H₂O 分子简单、但液态 / 固态 / 气态是涌现属性。Claude 的 6 个原语工具简单、但代码审查 / 重构 / 部署是涌现能力。

4 个典型涌现模式

模式 1：Read + Edit = 理解 + 修改（代码审查 / Bug 修复）

Claude 先 Read 整个文件 → 推理代码逻辑 → 用 Edit 改具体行。不需要专门的代码审查工具，Read + Edit 组合就够。

模式 2：Bash + Grep = 查 + 改（批量重构）

Claude 用 Grep 找出所有匹配文件 → 用 Bash 跑 sed / awk 批量改。例：把 100 个 Python 文件的 print("debug:") 改成 logger.debug()，Grep 找文件 + Bash 跑 sed 改。

模式 3：Write + Bash = 生成 + 执行（写脚本并跑）

Claude 用 Write 写一个 .py 脚本 → 用 Bash 跑这个脚本。例：Claude 写一个数据迁移脚本、先 Write 到 disk、再 Bash 跑。

模式 4：Grep + Read + Edit = 搜 + 读 + 改（多文件修复）

Claude 用 Grep 找匹配行 → Read 上下文（前后 5 行）→ Edit 修复。例：把 requests.get(url) 改成 requests.get(url, timeout=30) 全项目替换。

4 个模式覆盖 80% 的 Claude 任务。涌现的力量：不需要专门工具、原语组合就够了。

涌现 vs 专门工具

反例：如果给 Claude 一个批量重构工具（专门工具），Claude 必须学这个工具的 API（参数 / 限制 / 错误处理）、反而更复杂。涌现方案：Claude 用 Grep + Bash 就能搞定、不需要学新工具。

涌现的力量在于 LLM 推理 + 原语组合、而不是工具功能堆砌。这是 AI Agent 时代和传统软件时代最大的不同。

设计哲学：约束产生创造力

Claude Code 的工具系统刻意克制——只内置 6 个核心工具 + N 个 MCP 工具、不写专门工具（不写代码审查工具 / 重构工具 / 部署工具）。这是有意为之、体现约束产生创造力的设计哲学。

为什么不写专门工具

• 工具稳定——Read / Write / Bash 一年没变、LLM 训练数据稳定。如果频繁加专门工具，LLM 要不断学新 API、反而降低能力。

• LLM 学习负担低——6 个核心工具、LLM 一次学完。如果有 50 个专门工具，LLM 选择困难、选错概率高。

• 跨任务通用——原语工具组合、可以处理任意任务。代码审查工具只能审查、部署工具只能部署、通用性差。

• 用户可预测——用户知道 Claude 能做什么（读 / 写 / 搜 / 执行 / 交互）、不需要看文档学专门工具。

约束 vs 自由的权衡

传统 IDE 哲学：工具越多越好（给开发者选择权）。

Claude Code 哲学：工具越少越好（给 LLM 约束）。

为什么？因为 AI Agent 不是开发者、不是用户主动调工具——是 LLM 推理调工具。LLM 推理受上下文长度 / 训练数据影响、工具多反而干扰推理。

约束的好处：LLM 在 6 个工具里深思熟虑地选；自由的坏处：LLM 在 50 个工具里乱选或选不到合适的。

类比：给一个学生出 6 道题（他认真做）vs 100 道题（他选简单的做）。约束让质量更高。

少即是多：Unix 哲学的 AI Agent 应用

Claude Code 的工具哲学 = Unix 哲学在 AI Agent 时代的应用。

Unix 哲学

Unix 哲学：一个程序只做一件事、但做好。程序之间通过管道（pipe）组合、产生复杂能力。例：cat file.txt | grep "error" | wc -l（cat 读文件 → grep 过滤 → wc 计数），3 个简单程序组合出统计错误行数的能力。

Unix 的核心：cat / grep / awk / sed 都是简单原语、但组合出无限可能。

Claude Code 工具哲学

类比 Unix：Read / Write / Grep / Bash 都是简单原语、组合出无限可能。

• cat 等价于 Read（读内容）。

• ls 等价于 Glob（列文件）。

• grep 等价于 Grep（搜内容）。

• shell 等价于 Bash（执行命令）。

• echo / sed / awk 都用 Bash 跑（执行命令）。

Claude Code 工具系统 = Unix 命令行的 LLM 化——同样的原语、同样的组合、但操作者从人变成 LLM。

Unix 哲学的 3 个核心

1. 组合性(composability)——小工具能组合、产出大能力。

2. 简单性(simplicity)——每个工具只做一个原子操作。

3. 统一性(uniformity)——所有工具的输入输出是文本流（plain text)、能互相管道。

Claude Code 工具系统也遵循这 3 个：组合性（Read + Edit）、简单性（每个工具只做一件事）、统一性（所有工具输入输出是结构化文本、LLM 能理解）。

工具使用的 4 个最佳实践

会用工具是基础、精通工具需要 4 个最佳实践。

最佳实践 1：精确描述意图（让 LLM 选对工具）

Claude 选工具的依据是用户说的话 + 工具的 description。如果意图模糊、Claude 可能选错工具。例：用户说看看这个文件，Claude 可能用 Read（读内容）或 Glob（列文件）或 Grep（搜内容）——含糊。改进：用户说读 src/api.py 的 100-200 行、意图精确、Claude 直接用 Read 带 offset/limit。

精确意图 = 减少 LLM 选择负担 = 更高效。

最佳实践 2：利用工具组合（不要 1 个工具 1 步到位）

不要追求 1 个工具完成任务、应该组合。例：用户说修复所有 print 调试、改进方案（单工具）：Claude 用 Read 找 print、改用 Edit 1 个 1 个改、慢。组合方案：Claude 用 Grep 找所有 print → Read 上下文 → Edit 改、快 10 倍。

工具组合 = 利用涌现 = 更高效。

最佳实践 3：利用 Bash 跑长任务（后台进程）

长任务（几分钟 / 几小时）不要让 Claude 阻塞等。用 Bash 后台跑、然后轮询。例：Claude 跑 pytest tests/ > /tmp/test.log 2>&1 & 启动后台进程、然后用 Bash 轮询 cat /tmp/test.log | tail -20 看进度、等结束看结果。

后台进程 = 不阻塞 Claude = 流畅体验。

最佳实践 4：利用 MCP 扩展（连接外部世界）

本地工具够不着的（连接 GitHub / Notion / 数据库）、用 MCP 扩展。第 19 讲讲过 5 个实战 MCP server、本讲强调：MCP 是工具系统的插件、不破坏原语哲学（每个 MCP 工具也是一个原子操作）。

MCP 扩展 = 不破坏约束 = 灵活扩展。

工具系统 vs Skills / SubAgent / Hooks 边界

前 19 讲我们学了 4 种扩展机制（SubAgent / Skills / Hooks / MCP)+ 第 20 讲加入工具系统作为底层。5 者的工程定位不同、不能互相替代。

5 者的工程定位

• Tools：内功——原子操作、LLM 调用的最底层。负责做原子动作。

• Skills：招式——LLM 推理该用就用、渐进披露。负责描述本地能力。

• SubAgent：分身——独立上下文、@name 显式调。负责复杂任务隔离。

• Hooks：门卫——事件驱动、硬约束。负责瞬间检查。

• MCP：桥梁——连接外部 API、标准化协议。负责调用外部世界。

5 者的工作层次不同：Tools 在内功层（最底层原子），Skill 在招式层（LLM 推理），HW 在门卫层（事件），MCP 在桥梁层（外部 API），SubAgent 在角色层（独立上下文）。

内功 vs 招式

类比武侠：Tools 是内功（九阳神功 / 易筋经），Skills / SubAgent / Hooks / MCP 是招式（太极拳 / 独孤九剑）。内功扎实了、招式随意；内功不扎实、招式花哨也打不过。

对 Claude 来说：Tools 是基础（LLM 推理调工具）、扩展机制是在工具之上构建的逻辑。如果不熟悉工具、Skills / SubAgent / Hooks / MCP 都没用——LLM 连原子操作都做不好、扩展机制再花哨也是空中楼阁。

5 者的协同

典型协同：Claude 用 Read（读 src/) + Grep（搜 print) + Edit（改）完成批量重构、整个过程只用基础工具；完成后用 SubAgent（code-reviewer）做代码审查，SubAgent 也用基础工具；最后用 Hook（stop-gate）做 4 步质量门控，Hook 也调基础工具（Read git status / Bash pytest）。

3 层结构：基础工具（原子） → 扩展机制（招式） → 工作流（组合）。这是 Claude Code 工程化的完整图景。

#!/usr/bin/env bash
# 工具组合的 4 个典型模式

# ===================================
# 模式 2:Bash + Grep = 查 + 改(批量重构)
# ===================================
# Claude 工作流:
# 1. Grep 找所有匹配文件
# 2. Bash 跑 sed / awk 批量改

# 例: 把所有 Python 文件的 print("debug:") 改成 logger.debug()
GREP_MATCHES=$(grep -rl 'print("debug:' src/ --include="*.py")
echo "找到文件: $GREP_MATCHES"

# 批量替换
for file in $GREP_MATCHES; do
  sed -i 's/print("debug: \(.*\)")/logger.debug(\1)/g' "$file"
done


# ===================================
# 模式 3:Write + Bash = 生成 + 执行(写脚本并跑)
# ===================================
# Claude 工作流:
# 1. Write 写脚本到 disk
# 2. Bash 跑这个脚本

# 例: 数据迁移
cat > /tmp/migrate.py << 'EOF'
import sqlite3
conn = sqlite3.connect('app.db')
conn.execute('ALTER TABLE users ADD COLUMN email TEXT')
conn.commit()
EOF

python /tmp/migrate.py

# Claude Code 工具系统的 4 个设计原则

## 原则 1:原子性(Atomicity)
- 每个工具只做一件事
- Read 只读不写,Edit 只改不查
- 工具之间不互相依赖,可以独立调用
- 例: Bash 工具不内置"git push"专门命令,只跑任意 shell 命令
      Claude 自己跑 `git push` 就是 Bash 原子操作

## 原则 2:稳定性(Stability)
- 核心工具 1+ 年不变
- Read / Write / Bash 等 6 个工具是 LLM 训练数据的稳定 API
- 频繁加专门工具会破坏稳定性,LLM 要不断学新 API

## 原则 3:LLM 友好(LLM-Friendly)
- 工具的 description 写得清晰,LLM 能理解何时用
- 输入输出是结构化文本(LLM 推理友好)
- 错误信息明确,LLM 能根据错误重试
- 例: Read 工具的 description: "Read a file from the local filesystem."
      LLM 看到就知道读文件用这个

## 原则 4:跨任务通用(Cross-Task General)
- 工具不绑定具体任务
- 代码审查不写专门工具,用 Read + Grep + Edit 组合
- 部署不写专门工具,用 Bash 跑 deploy 脚本
- 通用性 = 工具少 + 组合强

# === 4 个原则的相互关系 ===
# 原子性  →  工具简单,组合强
# 稳定性  →  LLM 训练数据稳,选对工具
# LLM 友好  →  工具易学易用
# 跨任务通用  →  工具复用率高

# === 反例:违反 4 个原则的专门工具 ===
# 写一个代码审查工具:
# - 违反原子性(内部包含 Read + Grep + Edit 多个操作)
# - 违反稳定性(每次改审查规则,工具 API 变)
# - 违反 LLM 友好(LLM 要学专门工具的 API)
# - 违反跨任务通用(只能审查,不能重构 / 部署)

# → 改进: 不用专门工具,用 Read + Grep + Edit 组合 + Skill 描述
#          既符合原子性,又跨任务通用

⚠️ 常见坑

⚠️ 给 LLM 过多专门工具（自己写代码审查工具、结果 Claude 不会用基础工具、反而降低能力）

专门工具反噬陷阱：为了让 Claude 更专业、写一堆代码审查工具 / 重构工具 / 部署工具、结果 Claude 选择困难（50 个工具挑一个）、反而降低能力；而且每个专门工具的 API 变、LLM 训练数据失效。修正：坚持原语 + 组合——让 Claude 用 Read + Grep + Edit 组合做代码审查、用 Bash + Write 组合做部署。不写专门工具、用 Skill 描述 + 原语组合实现专门能力。判断标准：你的工具列表里有 >10 个专门工具吗？有、精简到原语。

⚠️ 工具配置过深（每个工具 100+ 参数、LLM 选择困难、只暴露必要参数）

工具参数爆炸陷阱：工具配置时把所有可能参数都暴露——Read 工具有 100+ 参数（可选 offset / limit / encoding / max_tokens / mode ...），LLM 选错概率高。修正：只暴露必要参数——Read 工具暴露 file_path（必填）+ offset / limit（常用）、其他高级参数（encoding / mode）用工具默认值。判断标准：工具 description 里的参数列表 >10 个？精简到 <5 个必填/常用。

⚠️ 工具输出过大（Read 1GB 文件卡死、Grep 没 limit 把上下文塞满、必须给合理默认值）

输出爆炸陷阱：Read 工具读 1GB 文件、Claude 上下文塞满卡死；Grep 搜 10k 文件、匹配行 100k 行、塞满上下文。修正：工具必须有合理默认值——Read 限 ≤2000 行（用 offset/limit 分段读）；Grep 限 max-results=100（超过提示 Claude 用 --include 缩小范围）；Bash 限 timeout=30s（长任务用后台进程）。判断标准：你的工具默认值能防输出爆炸吗？Read / Grep / Bash 都有合理限制？没有、补默认。

⚠️ 不利用工具组合（每步单工具调用、没组合出管道、效率低；Read+Edit 一步到位比 Read 一次、Edit 一次高效）

不组合低效陷阱：Claude 完成任务时每步只调 1 个工具——Read 一次 → 推理 → Edit 一次 → 推理 → Bash 一次、来回 6 次工具调用、慢。改进：用工具组合——Grep 一次找所有匹配 → Read 一次读上下文 → Edit 多次改、3 次组合工具调用搞定、快 2 倍。修正：Claude 任务前先规划用什么组合、而不是一步一看。判断标准：Claude 完成任务用了 >10 次工具调用、可能是没组合。观察工具调用次数、反思是否应该组合。

💡 一句话备忘

工具系统是 Claude Code 的内功——5 类原子操作（读 / 写 / 搜 / 执行 / 交互）+ 十几个原语工具 + 工具涌现（组合产生复杂能力）、体现少即是多、约束产生创造力的设计哲学、这是 Unix 哲学在 AI Agent 时代的应用。
